# Paymaster selection for a sponsored UserOp

Entry points: `UserOpSender.trySendSponsored` (delegation, vault sweeps/redeems, token sends) and `ContractInteractionService.prepareBidUserOp` (bids). Both call `buildPaymasterAndData` in `src/services/paymaster/index.ts`.

1. `buildPaymasterAndData` has exactly one candidate: the Simplex paymaster (`provider/simplex.ts`). No Simplex address for the chain returns `type: "none"` with `"no paymaster configured"` and the caller falls back to native / the EntryPoint deposit. When the caller passes `prefund` (both do) and the chain has an EntryPoint configured, it is gated on its EntryPoint deposit: `EntryPoint.balanceOf(paymaster)` must cover `(baseGas + VERIFICATION_GAS_LIMIT_PERMIT2 + POST_OP_GAS_LIMIT_SIMPLEX) * maxFeePerGas * DEPOSIT_HEADROOM_PERCENT / 100` or it is skipped with a warn and that reason. The gate runs *before* `buildSimplexPaymasterData`, which may send a bootstrap approve tx that must not happen for a paymaster that cannot sponsor. A failed deposit read fails open (candidate kept) — a transient RPC error degrades to the bundler's own precheck, never worse.

2. `buildSimplexPaymasterData` scans configured stablecoins (USDC, then USDT — `configuredFeeTokens`) for a balance of at least one whole token and a Permit2 allowance covering $5, scaled by each token's decimals (`selectToken`). It stops at the first ready token; an unapproved USDC balance therefore does not block ready USDT. If none is ready, it uses the first balance-qualified token for the existing bootstrap path. Selection only reads state; it sends no approval transactions. When no token meets the balance minimum it returns the balances it read instead of paymaster data, and step 1 records them as `simplex: solver USDC balance 0 < 1000000, USDT balance 0 < 1000000`, or `simplex: no fee token configured`. Otherwise:
   - `permit2 = configService.getPermit2Address(chain)` must be configured and `paymasterSupportsPermit2` (a cached `PERMIT2()` read on the paymaster) must hold, else the builder throws an error naming the reason; `buildPaymasterAndData` catches it, warns, and returns it as the `type: "none"` reason. Then:
     - Permit2 allowance at or above $5 — the common case: straight to `buildPermit2Mode`.
     - Allowance short **and** `permitBootstrap` set **and** `tokenSupportsPermit` (a `version()` probe): `buildPermitMode` signs an EIP-2612 permit (`permit.ts`, `deadline = maxUint256`) and packs mode `0x00` (150 bytes) with `VERIFICATION_GAS_LIMIT_PERMIT`. No tx is sent, which is the point — see the delegation section below. An existing allowance to the paymaster is not consulted; the contract has no mode that spends one.
     - Allowance short otherwise: `ensureFundedApprove` → `sendFundedApprove`. The wrapper dedups by (chain, token, owner): the bid path and the vault/token-send path are scheduled independently, so both can find the allowance missing at once and race for the EOA's transaction nonce; the second caller rides the first's promise. `sendFundedApprove` itself pre-checks the native balance against the whole sequence, reset a stale non-zero allowance to zero first (USDT rule), then `approve(Permit2, max)` from the solver EOA, up to two txs, each waiting two confirmations. Then `buildPermit2Mode`.
     - `buildPermit2Mode`: random 256-bit nonce (`randomPermit2Nonce`), `deadline = now + PERMIT2_DEADLINE_SECONDS`, `signPermit2Transfer` (`permit2.ts`, canonical v4 typed data, 65-byte signature) and pack mode `0x02` (182 bytes) with `VERIFICATION_GAS_LIMIT_PERMIT2`. The nonce is a bitmap slot rather than a counter, so ops built concurrently on one chain never collide.

   Step 1's deposit gate prices against `VERIFICATION_GAS_LIMIT_PERMIT` (250k) when `permitBootstrap` is set and `VERIFICATION_GAS_LIMIT_PERMIT2` (200k) otherwise, since the bootstrap op does not know which mode it will land in until the allowance is read.

3. Back in `UserOpSender.trySendSponsored`, the bundler gas price is fetched *before* paymaster selection so the deposit gate can price the op's max prefund (from the caller's fixed limits, or the generous fallbacks when estimating later). The EIP-7702 authorization thunk is still resolved only after paymaster data is built, because the bootstrap approve is a tx from the same EOA and an authorization signed earlier would carry a stale nonce (bundler reject). Then `EntryPoint.getNonce`, estimation (or the caller's fixed limits), signing of the packed userOp typed data, `eth_sendUserOperation`, and receipt polling.

4. On chain (`evm/src/utils/SimplexPaymaster.sol`, unchanged): `_validatePaymasterUserOp` executes the permit for mode 0 after checking the token is registered and active; `_fetchDetails` accepts mode bytes `0x00` and `0x02` (`InvalidMode` otherwise, so a mode `0x01` payload with a standing allowance behind it is refused before any transfer) and, for mode 2, returns the permit deadline as `validUntil`; `_prefund` pulls mode 0 through the base `transferFrom` on the permit's allowance and mode 2 through `Permit2.permitTransferFrom` (owner = `userOp.sender`, to = paymaster, requestedAmount = oracle-derived prefund, capped by the signed amount); postOp refunds the unused part to the sender.

Governance delivery and the relayer gate (`SimplexPaymaster.onAccept`, exercised by the relayer-gate cases in `evm/tests/foundry/SimplexPaymasterTest.t.sol`): the handler verifies the proof and the host calls `onAccept` with the handler's `msg.sender` as `incoming.relayer`. `onlyHost` runs first, then `_checkRelayer`, which reverts `UnauthorizedRelayer` when `_relayer` is set and the delivery came from anyone else, then the Hyperbridge source check, and only then is the kind byte read. The host records a refused delivery as undelivered, so the authorised relayer can resubmit it. A proxy from before the gate is armed by the `upgrade_paymaster` extrinsic carrying `migrate(relayer)` as init data: the upgrade's delegatecall keeps the host as `msg.sender`, `migrate` is host-only and a one-shot reinitializer to version 2, and `onlyFresh` keeps `initialize` off that proxy. Rotation is the `SetRelayer` request kind, dispatched by `set_paymaster_relayer`; both refuse zero, and the request itself must be delivered by the relayer on record.

# Simplex API

Everything the [dashboard](/developers/evm/simplex/dashboard) does goes through an HTTP API on the solver. You can call it directly from a script, a cron job, or your own tooling. It takes and returns JSON, and it is served on the same address as the dashboard.

<Callout type="warn">
    The API has no authentication. Anyone who can reach it can do everything the dashboard can,
    including sending tokens out of the wallet. Keep it on loopback or a private Unix socket. To reach
    it from another machine, use SSH or the remote access tunnel, as the
    [dashboard page](/developers/evm/simplex/dashboard) describes.
</Callout>

## Base URL

The API listens where the dashboard does, which is `127.0.0.1:8686` by default. `--ui` moves it, `--ui-socket` serves it on a Unix socket instead, and `--no-ui` turns it off. See [Command-line flags](/developers/evm/simplex/dashboard#command-line-flags).

The examples in this section keep the base URL in a shell variable:

```bash lineNumbers
SIMPLEX=http://127.0.0.1:8686
curl -s $SIMPLEX/api/status
```

On a Unix socket, pass the socket to curl. The host in the URL is not checked there, so `localhost` is fine:

```bash lineNumbers
curl -s --unix-socket "$HOME/.simplex-runtime/ui.sock" http://localhost/api/status
```

## Rules for every call

- A request with any method other than `GET` or `HEAD` must carry the header `X-Simplex-UI: 1`. Without it, the server answers `403`. A web page in your browser cannot add this header to a cross-origin request, so it cannot call the API behind your back.
- Over TCP, the `Host` header must be an IP address or `localhost`. When the API is bound to loopback, it must be a loopback address. A DNS name is refused with `403`, which blocks DNS rebinding. curl sends an acceptable `Host` when the URL uses the IP address.
- Request bodies are JSON, up to 1 MiB.
- Responses are JSON and are never cached, except for the three [streams](#streams).
- Errors are JSON in the form `{ "error": "..." }`. The message says what went wrong.

## Setup mode and operator mode

The server runs in one of two modes. When `simplex run` finds no config, it opens the [setup wizard](/developers/evm/simplex/api/setup), and the server is in setup mode. When the wizard starts the filler, the server switches to operator mode on the same address. With a config, it starts in operator mode.

In setup mode, only `/health`, `/api/status`, `/api/stop` and the setup routes answer. Every other route answers `409` with `Filler is not running`.

In operator mode, the setup routes answer `410`. The exceptions are the four [validation probes](/developers/evm/simplex/api/setup#validation-probes), which the dashboard's forms still use.

[`GET /api/status`](/developers/evm/simplex/api/status#get-apistatus) and [`GET /health`](/developers/evm/simplex/api/status#get-health) report the mode. They call setup mode `init`.

## Status codes

| Code | Meaning |
|---|---|
| `200` | Done. |
| `201` | A device was paired for remote access. |
| `202` | Accepted and still in progress: a stop, or the wizard starting the filler. |
| `400` | The request was refused. The message says why. |
| `403` | The `X-Simplex-UI` header is missing, the `Host` header is not allowed, or remote access was changed through the tunnel. |
| `404` | No such route, order or device. |
| `405` | The route exists, but not with this method. |
| `409` | The filler is not running, or a feature the route needs is not configured. |
| `410` | A setup route was called after setup finished. |
| `500` | The action failed on the solver, for example a vault transaction that reverted. |
| `502` | The orderbook, or a push notification service, could not be reached. |
| `503` | Notifications are temporarily unavailable. |

## Streams

Three routes stream [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) instead of returning JSON once: [`/api/events`](/developers/evm/simplex/api/activity#get-apievents), [`/api/logs/stream`](/developers/evm/simplex/api/logs#get-apilogsstream) and [`/api/notifications/stream`](/developers/evm/simplex/api/notifications#get-apinotificationsstream). Each event is a `data:` line holding one JSON object.

Read one with `curl -N`, which prints events as they arrive:

```bash lineNumbers
curl -sN $SIMPLEX/api/events
```

`/api/events` and `/api/notifications/stream` send a `:keepalive` comment every 25 seconds, so a quiet stream is not mistaken for a dead one.

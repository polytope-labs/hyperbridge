# Simplex

The `Simplex` class is a running intent solver. It boots every service, delegates the solver account
where solver selection is active, scans the configured chains, and exposes every runtime control as a
namespaced controller.

For a task-oriented walkthrough see [Simplex](/developers/sdk/simplex); for the standalone binary see
[the Intent Gateway solver docs](/developers/evm/simplex/overview).

```typescript lineNumbers
class Simplex extends EventEmitter
```

```bash lineNumbers
npm install @hyperbridge/simplex
```

## Static Methods

### Simplex.start(options)

Boots a solver and starts it. Resolves once chains are resolved, EIP-7702 delegation is in place
where solver selection is active, and the scanners are live.

```typescript lineNumbers
static async start(options: SimplexOptions): Promise<Simplex>
```

**Parameters:**

| Name | Type | Description |
|------|------|-------------|
| `options.config` | `SimplexConfig` | The solver configuration. The shape the binary's `filler-config.toml` parses into, minus `[simplex.signer]` — that block belongs to `FillerConfigFile` and is resolved into `options.signer`. `simplex.blockScanIntervalSeconds` sets the scan rate of a scanner the solver builds; one passed via `orderScanner` keeps its own |
| `options.signer` | `Signer` | Optional. How the solver signs — bids, UserOperations, EIP-7702 delegation and every transaction it sends. Required unless every chain is watch-only. Passing a parsed config *file* that carries a `simplex.signer` block, with no `signer`, throws |
| `options.data` | `SimplexDataStore` | Optional. Persistence backend. Defaults to `MemoryDataStore`, which is lost on exit |
| `options.configPath` | `string` | Optional. Where the config was loaded from. Informational — it is surfaced in logs and to the bundled dashboard. The library never writes it; use `onConfigChange` to persist runtime edits |
| `options.watchOnly` | `boolean` | Optional. Forces watch-only on every chain, whatever the config says |
| `options.logger` | `LogSink` | Optional. Where to send log records, one NDJSON line each. Omit and the solver logs nothing |
| `options.orderScanner` | `OrderScanner` | Optional. Gateway events for this solver. Pass one instance to several solvers to share a scan loop. Omit and the solver builds a private scanner and closes it on `stop()` |
| `options.onConfigChange` | `(config: SimplexConfig) => void \| Promise<void>` | Optional. Called after any mutation that changes the effective config |

**Returns:** `Promise<Simplex>` — a solver that is already scanning

**Throws:** If the config is invalid, a chain's RPCs are unreachable, or EIP-7702 delegation fails on
every chain. A partially-started solver is never returned, so there is no readiness state to poll.

**Example:**

```typescript lineNumbers
import { Simplex, privateKeySigner } from "@hyperbridge/simplex"
import { SqliteDataStore } from "@hyperbridge/simplex/sqlite"

const simplex = await Simplex.start({
    config,
    signer: privateKeySigner(process.env.SOLVER_KEY as `0x${string}`),
    data: new SqliteDataStore("./simplex-data"),
    onConfigChange: async (config) => db.settings.put("filler-config", config),
})
```

<Callout type="warn">
    The default `MemoryDataStore` keeps nothing across a restart. A solver that submits bids should
    pass a durable store: a successful bid locks a deposit that is only reclaimable by retraction,
    and the retraction sweep finds what to reclaim by querying the bid store.
</Callout>

## Lifecycle

### pause()

Stops analysing and filling new orders. Monitoring continues and in-flight fills complete; orders
arriving while paused are dropped, not queued, so resuming does not replay them. The pause is
written to the state store, so it survives a restart.


Drains the solver, unwinds every vault position marked `redeemOnShutdown` back to its underlying
asset, and closes the data store. Idempotent, and never calls `process.exit`.

## Events

### on(event, listener) / once(event, listener) / off(event, listener)

Payloads are inferred from the event name, so a wrong field is a compile error. A misspelled event name is not — the catch-all overload that keeps `EventEmitter` compatible accepts any string.

```typescript lineNumbers
on<E extends keyof SimplexEvents>(
    event: E,
    listener: (payload: SimplexEvents[E]) => void,
): this
```

| Event | Payload |
|------|---------|
| `order:detected` | `{ order: Order; transactionHash: string }` |
| `order:skipped` | `{ orderId: string; reason: string }` |
| `order:filled` | `{ orderId: string; txHash?: HexString; chainId?: number; volumeUsd?: number; profitUsd?: number }` |
| `order:executed` | `{ orderId: string; success: boolean; strategy?: string; commitment?: HexString; txHash?: HexString; error?: string }` |
| `order:timing` | `{ orderId: string; phase: "evaluation" \| "confirmation" \| "queue_wait" \| "execution"; durationSec: number }` |
| `order:filled-onchain` | `{ commitment: HexString; filler: string; chainId: number }` |
| `order:fill-observed` | `{ commitment: HexString; filler: string; chainId: number; txHash?: string; ours: boolean }` — every `OrderFilled` on a configured chain; `ours` says whether this solver won it |
| `limit-order:posted` | `{ order: LimitOrder }` — `limitOrders.create` stored the order and the orderbook accepted it (or, for a same-asset order, it was stored unposted) |
| `limit-order:rejected` | `{ order: LimitOrder; code: string; message: string }` — the order was stored but the orderbook refused or never answered the posting |
| `limit-order:cancelled` | `{ order: LimitOrder }` — `limitOrders.cancel` |
| `limit-order:resized` | `{ order: LimitOrder; delivered: string }` — a fill drew the order down by `delivered` (1e18 scale) and it went back on the book at its new size |
| `limit-order:filled` | `{ order: LimitOrder }` — a fill took the order under the orderbook's dust floor, so it closed |
| `rebalance` | `{ success: boolean; transferCount?: number; executedCount?: number; error?: string }` |
| `activity` | `ActivityEvent` — every row written to the activity store |

**Example:**

```typescript lineNumbers
simplex.on("order:filled", ({ orderId, profitUsd, chainId }) => {
    metrics.fills.inc({ chain: String(chainId) })
    log.info({ orderId, profitUsd }, "filled")
})
```

This is the whole telemetry surface — anything the solver knows about its own activity arrives
through these events, so metrics and alerting build on them with no privileged access.

## LimitOrderController

`simplex.limitOrders`. The operator's limit orders: what the solver offers to pay, and what the
HyperFX orderbook in `config.orderbook` advertises on its behalf. Every incoming swap is priced
against the open orders, and one that matches none is not filled. The operator workflow is in
[Limit orders](/developers/evm/simplex/limit-orders).

### create(request)

Validates, stores and posts one limit order, then emits `limit-order:posted` or
`limit-order:rejected`.

```typescript lineNumbers
create(request: CreateLimitOrderRequest): Promise<PostedLimitOrder>
```

**Parameters:**

| Name | Type | Description |
|------|------|-------------|
| `request.fillChain` | `string` | State machine id the order fills on, e.g. `"EVM-8453"`. Must be a configured chain |
| `request.tokenIn` | `string` | Symbol the solver takes in |
| `request.amountIn` | `string` | Whole tokens taken in, as a decimal string: `"1000"`, `"1500.25"`. At most 18 decimal places |
| `request.tokenOut` | `string` | Symbol the solver pays out |
| `request.amountOut` | `string` | Whole tokens paid out, as a decimal string |
| `request.acceptedSources` | `string[]` | Source chains whose swaps the order serves. Non-empty, no repeats |
| `request.ttlSecs` | `number` | Optional. How long the order lives, and the TTL of its posting. Defaults to `orderbook.defaultTtlSecs`, or 365 days. Nothing renews it |

The two amounts fix the rate and the side. `tokenIn` and `tokenOut` must be the two sides of a book
the orderbook lists (see `books()`), in either orientation: taking the book's base in and paying its
quote out is a `BID`, the other way an `ASK`. The stored rate is rounded in the solver's favour. A
same-asset order (`tokenIn === tokenOut`) is stored and prices swaps locally but is never posted,
and must pay out no more than it takes in.

**Returns:** `PostedLimitOrder` — `{ order: LimitOrder; result }`, where `result.kind` is
`"accepted"`, `"unchanged"`, `"rejected"` (with `code` and `message`), `"failed"` (the request got
no usable answer, with `code`, `message` and `retryable`) or `"unposted"` for a same-asset order.

**Throws:** `LimitOrderValidationError` before anything is stored when the request is malformed, the
fill chain is not configured, the orderbook does not serve the fill chain or a source, the
orderbook lists no `tokenIn` on a source, the pair is not a listed book, the TTL is under the
orderbook's minimum, `amountOut` is under the orderbook's dust floor for `tokenOut`, a symbol does
not resolve on the fill chain, the wallet plus configured vaults on the fill chain hold less
`tokenOut` than `amountOut`, or EIP-7702 delegation on the fill chain cannot be set up. A posting
the orderbook refuses does not throw: the row is kept as `rejected` with the reason in `lastError`.
A retryable `failed` posting leaves the order `open` with `lastError` set, and reconciliation posts
it again.

**Example:**

```typescript lineNumbers
const { order, result } = await simplex.limitOrders.create({
    fillChain: "EVM-8453",
    tokenIn: "USDC",
    amountIn: "10000",
    tokenOut: "CNGN",
    amountOut: "13900000",
    acceptedSources: ["EVM-1", "EVM-8453"],
})
```

### cancel(id)

nothing new draws on it even if the orderbook call fails; a refusal is recorded in `lastError`.


**Returns:** `{ order: LimitOrder; result }`, `result.kind` being `"cancelled"`, `"rejected"` or

### profitability(period, tzOffsetMinutes?)

What your fills earned over a period: `"7d"`, `"30d"`, `"12w"`, `"12m"` or `"all"`. Profit is the
change the period's fills made to what the solver holds, each token valued at its latest rate, and
it is compared with the inventory the period began with. `tzOffsetMinutes` is what
`getTimezoneOffset()` returns on the clock the buckets should be cut on, and defaults to UTC.

```typescript lineNumbers
profitability(period: ProfitPeriod, tzOffsetMinutes?: number): Promise<Profitability>
```

The result holds `totals`, one `series` entry per bucket, one `books` entry per pair,
`startInventory`, `estimatedFills` and `unpricedTokens`, as plain numbers in whole tokens and
dollars. The [profitability route](/developers/evm/simplex/api/limit-orders#get-apianalyticsprofitability)
describes each field. It reads the data store and the balances already in memory, so it answers
without an orderbook configured.

### books()

accepts per token, and the tokens it registers on each chain it serves.


### LimitOrder

Amounts and prices are decimal strings at 1e18, the orderbook's unit, whatever decimals the tokens
use on their own chains.

| Field | Type | Description |
|------|------|-------------|
| `id` | `string` | Stable across every repost |
| `book`, `base`, `quote` | `string` | The orderbook book and its symbols |
| `side` | `"BID" \| "ASK"` | `BID` takes the base in and pays the quote out; `ASK` the reverse |
| `fillChain` | `string` | State machine id the order fills on |
| `price` | `string` | Quote per 1 base, as signed |
| `size` | `string` | Output offered when the order was created |
| `remaining` | `string` | Output not yet delivered |
| `reserved` | `string` | Output held by bids that have neither filled nor been retracted |
| `acceptedSources` | `string[]` | Never empty |
| `ttlSecs` | `number` | |
| `expiresAt` | `string \| null` | When the order and its posting lapse |
| `status` | `LimitOrderStatus` | `open`, `resizing` (a fill is being settled), `filled`, `cancelled`, `expired` or `rejected` |
| `commitment` | `string \| null` | The live posting's commitment; `null` while nothing is posted |
| `orderNonce` | `string` | Bumped on every repost |
| `bookExpiresAt`, `bookPrice` | `string \| null` | The live posting's expiry, and its price after the orderbook's fee |
| `lastError` | `string \| null` | The last refusal, as `"CODE: message"` |
| `createdAt`, `updatedAt` | `string` | SQLite-style `"YYYY-MM-DD HH:MM:SS"` in UTC |

`LimitOrderFill`: `id`, `limitOrderId`, `commitment` (the swap it settled), `bid`, `amount` (what
it drew the order down by, 1e18 in the payout token), `amountIn` (what it took in, 1e18 in the
token the order takes in, or `null` for a fill recorded before it was kept), `transactionHash`,
`filledAt`.

### Over HTTP

The binary's operator server exposes the same controller. Mutating requests need the
`X-Simplex-UI: 1` header. A validation error is a `400`, an unreachable orderbook a `502`, and an
unknown id a `404` on `GET` and a `400` on `DELETE`. The
[limit orders API reference](/developers/evm/simplex/api/limit-orders) documents each route.

| Route | Controller call | Response |
|------|-----------------|----------|
| `GET /api/limit-orders?status=&chain=&book=` | `list({ status, fillChain: chain, book })` | `{ orders: LimitOrder[] }` |
| `POST /api/limit-orders` | `create(body)` | `{ order, result }` |
| `GET /api/limit-orders/:id` | `withFills(id)` | `{ order, fills, bids }` |
| `DELETE /api/limit-orders/:id` | `cancel(id)` | `{ order, result }` |
| `GET /api/orderbook/books` | `books()` | `{ books, minOrderSizes, chains }` |
| `GET /api/analytics/profitability?period=&tz=` | `profitability(period, tz)` | `Profitability` |

### Lifecycle

While the solver runs, a fill draws its order down by what was delivered and reposts the remainder,
closing it as `filled` once what is left is under the dust floor. The solver heartbeats the
orderbook while anything is posted, reconciles against the orderbook's copy every
`orderbook.reconcileIntervalSecs` (default 300) — withdrawing entries no order owns and reposting
orders whose entry has gone — and sweeps expired orders every 30 seconds.

## ChainController

`simplex.chains`. Chains can be added, removed and repointed without a restart.

### list()

```typescript lineNumbers
list(): ChainView[]
```

**Returns:** `{ chainId, stateMachineId, rpcUrls, bundlerUrl, watchOnly }` per chain.

### add(chain)

Brings a chain into the running solver: registers it, delegates on it if solver selection is active,
then starts its scanner.

```typescript lineNumbers
add(chain: ChainInput): Promise<ChainView>
```

**Parameters:**

| Name | Type | Description |
|------|------|-------------|
| `chain.rpcUrls` | `string[]` | One or more endpoints. Multiple enables quorum log scanning |
| `chain.bundlerUrl` | `string` | ERC-4337 bundler, required to submit fill UserOperations |
| `chain.watchOnly` | `boolean` | Optional. Monitor without filling |

`scanner.addChain(...)` first, then this. On a scanner the solver owns, it is added for you.

### remove(chainId)

Drains in-flight fills first, then stops scanning the chain and drops it from the config.

```typescript lineNumbers
remove(chainId: number): Promise<void>
```

**Throws:** If a vault entry still names the chain. Vaults hydrate per chain at boot, and one left
behind would fail the next start.

### setRpcUrls(chainId, rpcUrls)

Repoints a chain at new endpoints. Probes them first, then drops the cached viem clients and swaps
the scan loop's endpoints **keeping its block cursor**, so the change leaves no gap in the scanned
block range.

```typescript lineNumbers
setRpcUrls(chainId: number, rpcUrls: string[]): Promise<void>
```

**Throws:** If the endpoints share a hostname, are unreachable, answer for a different chain, or
belong to a scanner you supplied — see [Scanner ownership](#scanner-ownership).

### setBundlerUrl(chainId, bundlerUrl)

```typescript lineNumbers
setBundlerUrl(chainId: number, bundlerUrl: string): Promise<void>
```

### setWatchOnly(chainId, watchOnly)

Monitor without filling. Takes effect on the next order.

```typescript lineNumbers
setWatchOnly(chainId: number, watchOnly: boolean): Promise<void>
```

On a solver started without a `signer`, `setWatchOnly(chainId, false)` throws — and `add` defaults a
new chain to watch-only, rejecting an explicit `watchOnly: false`. A signerless start runs on a
generated throwaway key that holds no funds and dies with the process, so watch-only is a one-way
door there: filling would burn bids from an address nobody controls.


## VaultController

`simplex.vaults`. ERC-4626 treasury vaults the solver sources fills from and sweeps idle balance into.

```typescript lineNumbers
list(): VaultToml[]
preflight(vaults: VaultToml[]): Promise<void>
set(vaults: VaultToml[], options?: { sweepIntervalMs?: number }): Promise<void>
sweepNow(): Promise<VaultSweepResult>
redeemAll(): Promise<void>
```

`preflight` hydrates a prospective set against chain state without touching the live venue, so
unconfigured chains, same-asset duplicates and non-vault addresses surface before you commit to
`set`. `sweepNow` deposits wallet balance above each vault's threshold down to its floor and
returns what happened: `submitted` lists each batch with its deposits, and `skipped` names every
vault the pass left alone with a reason — `below-threshold` (the wallet has not reached its trigger),
`sweeping-disabled` (no threshold configured) or `deposits-closed` (the wallet is over its trigger
but the vault reports `maxDeposit(solver) == 0`, as a `StreamingYieldVault` does while a tranche
vests). The periodic sweep uses the same pass and logs a warning the first time a vault turns a
due deposit away. `redeemAll` unwinds every position flagged `redeemOnShutdown` back to its
underlying asset; positions without the flag are left in place.

```typescript lineNumbers
interface VaultSweepResult {
  submitted: { chain: string; txHash: HexString; sponsored: boolean; deposits: VaultSweepDeposit[] }[]
  skipped: VaultSweepSkip[]
}
interface VaultSweepDeposit { vault: HexString; asset: HexString; symbol: string; decimals: number; amount: bigint }
interface VaultSweepSkip {
  chain: string; vault: HexString; asset: HexString; symbol: string; decimals: number
  reason: "sweeping-disabled" | "below-threshold" | "deposits-closed"
  walletBalance?: bigint; threshold?: bigint; maxDeposit?: bigint   // base units
}
```

**Throws:** `set`, `sweepNow` and `redeemAll` throw if the solver was started without a vault treasury. `list` returns `[]` and `preflight` does not require one.

## AssetController

`simplex.assets`. Symbol-to-address resolution for the configured chains.

```typescript lineNumbers
add(defs: Record<string, AssetDefinition>): Promise<void>
resolve(symbol: string, chain: string): HexString | null
```

`add` registers custom tokens the built-in registry does not ship. Existing symbols cannot be
redefined — repointing one under a running market would silently redirect its fills. `resolve`
returns `null` when the asset is not deployed or not known on that chain.

The registry ships USDC, USDT, DAI, CNGN, USDR, ZARP, EURC, XSGD and TRYB.

## WalletController

`simplex.wallet`.

```typescript lineNumbers
get address(): HexString
balances(): BalanceSnapshot
send(params: { chain: string; token: string; amount: string; to: HexString }):
    Promise<{ txHash: string; sponsored: boolean; redeemed: boolean }>
history(limit?: number): Promise<WalletTx[]>
```

`balances()` returns the last refreshed snapshot — `updatedAt` is `null` until the first refresh
lands, and the shape is `{ updatedAt, chains: ChainBalanceRow[], hyperbridge? }`. `send` redeems
vault shares to the recipient when the token is held in a vault, and reports whether a paymaster
sponsored the gas. `history` covers operator sends plus vault sweeps and redeems, newest first.

## RebalanceController

`simplex.rebalancing`.

```typescript lineNumbers
set(rebalancing: RebalancingConfig | undefined): Promise<void>
trigger(): Promise<unknown>
```

`set` replaces the settings; trigger checks read them live. It cannot *enable* rebalancing on a solver that booted without it — the service is constructed at boot — so that still needs a restart. `trigger` runs a check now instead of
waiting for the timer, and throws if the solver was started without rebalancing configured.

## Signing

### Signer

The signing contract a solver runs on. `Simplex.start({ signer })` takes an implementation; the
bundled ones below are ordinary implementations with no privileged access. Nothing on it is a viem
type, so satisfying it never requires matching this package's viem version.

```typescript lineNumbers
interface Signer {
    /** The address every fill, bid and delegation is attributed to. */
    address: HexString
    /** Names the backend in logs. */
    mode: string

    /** EIP-712. Signs every bid UserOperation and every paymaster permit. */
    signTypedData(typedData: TypedDataPayload): Promise<HexString>
    /** The EIP-7702 delegation that makes this account a solver. */
    signAuthorization(auth: AuthorizationRequest): Promise<Signature>
    /** Returns the signed, RLP-encoded transaction, ready to broadcast. */
    signTransaction(tx: SignerTransaction): Promise<HexString>
}

interface Signature {
    r: HexString
    s: HexString
    yParity: number
}
```

Each operation names what is being authorised rather than handing over a digest, so a custody
provider's policy engine can read it. A backend that only signs digests should not implement this by
hand — pass its `sign(hash)` to `digestSigner`.

Each method returns something different, and the difference is the part that trips an implementation:

| Method | Return exactly |
|--------|----------------|
| `signTypedData` | The 65-byte `r ‖ s ‖ v` signature as 0x-hex (132 characters), `v` **27 or 28** — what `eth_signTypedData_v4` and viem's `signTypedData` produce. On-chain validation recovers against this form |
| `signAuthorization` | The **split** signature `{ r, s, yParity }`: `r`/`s` as 32-byte 0x-hex, `yParity` strictly **0 or 1** (subtract 27 from a legacy `v` — anything else is rejected, because EIP-7702 would otherwise skip the mis-encoded tuple silently). Split because the authorization is embedded field-by-field in the transaction |
| `signTransaction` | The **whole signed transaction** — typed-envelope RLP as `eth_sendRawTransaction` takes it (`0x02…` for EIP-1559, `0x04…` for set-code), not a bare signature. From a signed digest, viem's `serializeTransaction(tx, signature)` produces it |

`signTypedData` takes no chain id: EIP-712 carries it in `domain.chainId`, which is what the digest
covers and what a backend scoping a signing request to a chain reads.

A solver needs a signer unless every chain is watch-only.

**Supporting types:**

| Type | Purpose |
|------|---------|
| `TypedDataPayload` | An EIP-712 payload: `domain?`, `types`, `primaryType`, `message` |
| `AuthorizationRequest` | The tuple an EIP-7702 signature covers: `chainId`, `contractAddress`, `nonce` |
| `SignerTransaction` | The transaction handed to `signTransaction`: `chainId`, `type?`, `to?`, `value?`, `data?`, `nonce?`, `gas?`, `maxFeePerGas?`, `maxPriorityFeePerGas?`, `authorizationList?` |
| `Eip7702Authorization` | A signed authorization tuple: `chainId`, `address`, `nonce` and the `Signature` fields |
| `DerivingSigner` | A `Signer` plus `accountIndex` and `derive(index)`, which returns the `Signer` for the wallet at that index |

### Implementations

| Function | Signature | Notes |
|----------|-----------|-------|
| `privateKeySigner(key)` | `(key: HexString) => Signer` | A raw key held in this process |
| `secretPhraseSigner(config)` | `(config: SecretPhraseSignerConfig) => DerivingSigner` | A BIP-39 secret phrase held in this process. `config` is `phrase` and an optional `accountIndex` (default 0, an integer from 0 to 2147483647); the wallet is `m/44'/60'/0'/0/accountIndex`. Throws on an invalid phrase or index |
| `validateSecretPhrase(phrase)` | `(phrase: string) => void` | Throws unless the phrase has 12, 15, 18, 21 or 24 words from the BIP-39 English wordlist and a valid checksum. The error never quotes the phrase |
| `canDerive(signer)` | `(signer: Signer) => signer is DerivingSigner` | Type guard: whether a signer has `accountIndex` and `derive(index)` |
| `turnkeySigner(config)` | `(config: TurnkeySignerConfig) => Promise<Signer>` | Turnkey signs transactions and EIP-7702 authorizations through its own structured encodings, so its policy engine sees both |
| `mpcVaultSigner(config)` | `(config: MpcVaultSignerConfig) => Signer` | Signs transactions through the vault API; hashes the authorization tuple itself, and serialises set-code transactions, since the structured request carries no authorization list |
| `viemSigner(account)` | `(account: LocalAccount) => Signer` | Adapts any viem local account. Falls back to `sign` for authorizations when the account has no `signAuthorization`; throws if it has neither, since the solver could then never delegate |
| `digestSigner(opts)` | `({ address, mode, sign }) => Signer` | Builds a signer from a backend that only signs 32-byte digests. `sign(hash)` must return the split `Signature` — `{ r, s, yParity }` with `yParity` 0 or 1, not the 65-byte hex most HSM APIs hand back (split one with viem's `parseSignature`). Does the EIP-712 hashing, EIP-7702 authorization hashing and transaction serialising for you, and rejects an out-of-range `yParity` rather than letting a legacy `v` produce signatures that recover to a stranger |
| `createSigner(config)` | `(config: SignerConfig) => Promise<Signer>` | Builds the signer a `[simplex.signer]` TOML block describes. The block is typed on `FillerConfigFile`, not `SimplexConfig` |
| `validateSignerConfig(config)` | `(config: SignerConfig) => void` | Throws on an incomplete TOML block |

**Example — a remote signing service:**

```typescript lineNumbers
import { digestSigner } from "@hyperbridge/simplex"

const signer = digestSigner({
    address: await hsm.address(),
    mode: "hsm",
    // Must resolve to { r, s, yParity } with yParity 0 or 1 — split a 65-byte
    // hex signature with viem's parseSignature. A backend handing back the
    // legacy v (27/28) is rejected rather than mis-encoded.
    sign: async (hash) => parseSignature(await hsm.sign(hash)),
})
```

<Callout type="info">
    Simplex builds the viem account its wallet clients run on from the signer, so a backend that
    does not already produce one has nothing to bridge. `viemSigner` is there for backends that do,
    and `digestSigner` for backends that only see hashes.
</Callout>

## Persistence

Five things survive a restart: the bids submitted, the operator's limit orders, the activity feed,
a daily record of inventory, and whether the operator paused. They live behind `SimplexDataStore`.

```typescript lineNumbers
interface SimplexDataStore {
    bids: BidStore
    activity: ActivityStore
    state: StateStore
    limitOrders: LimitOrderStore
    inventory: InventoryStore
    close?(): Promise<void>
}
```

Every method is async — the bundled SQLite adapter is synchronous underneath and returns resolved
promises. The async signature is what lets a consumer back these with Postgres, Redis or a hosted API.

### BidStore

```typescript lineNumbers
store(bid: BidInsert): Promise<void>
byCommitment(commitment: string): Promise<StoredBid | null>
byCommitments(commitments: string[]): Promise<StoredBid[]>
unretractedReclaimable(): Promise<StoredBid[]>
expiredUnretracted(maxAgeMs: number): Promise<StoredBid[]>
markRetracted(
    commitment: string,
    retractExtrinsicHash: string | null,
): Promise<boolean>
markDead(commitment: string): Promise<boolean>
claimReservation(commitment: string, bid?: string): Promise<LimitOrderHold[]>
byLimitOrder(limitOrderId: string, limit?: number): Promise<StoredBid[]>
recent(limit?: number): Promise<StoredBid[]>
failed(limit?: number): Promise<StoredBid[]>
byDateRange(from: Date, to: Date): Promise<StoredBid[]>
stats(): Promise<BidStats>
```

<Callout type="warn">
    The correctness-critical store. A successful bid locks a deposit only reclaimable by retraction,
    and the sweep finds what to reclaim by querying here — an implementation that loses writes leaks
    deposits. `store` must be durable before it resolves; do not buffer in memory and flush later.
</Callout>

`expiredUnretracted` returns bids that are successful or still pending, unretracted, and either older than `maxAgeMs`
or flagged dead. Dead bids ignore the age cut because their deposit is reclaimable immediately, so a
failed attempt retries on the next sweep rather than waiting out the TTL.

`markRetracted` is also called when the chain reports `BidNotFound`: bids only leave the pallet by
retraction, so "no bid" means there is nothing left to reclaim and no hash is available. Both mark
methods resolve `false` when nothing matched, which callers treat as success rather than an error.

`StoredBid`: `id`, `commitment`, `bid`, `extrinsicHash`, `blockHash`, `success`, `pending`, `error`,
`createdAt`, `retracted`, `retractedAt`, `retractExtrinsicHash`, `dead`, `reservations`.

Several bids can share a commitment — the solver sends one bid per matching limit order — so `bid`
(the identifier Hyperbridge files it under) tells them apart. `reservations` lists the
`{ limitOrderId, amount }` holds a bid took against limit orders; `claimReservation` hands them over
exactly once when the bid settles, for one named bid or every outstanding hold on the commitment.
`byLimitOrder` reads back the bids that drew on an order.

`pending` marks a submission that timed out with its extrinsic still in Hyperbridge's pool. It is
neither success nor failure: the extrinsic may yet land and reserve a deposit, so a pending row
counts as reclaimable in `unretractedReclaimable`, `expiredUnretracted` and the `pendingRetraction`
stat. Treating it as a plain failure is how a deposit goes unnoticed and unreclaimed. `createdAt` is SQLite-style
`"YYYY-MM-DD HH:MM:SS"` in UTC so it sorts lexicographically.

### ActivityStore

```typescript lineNumbers
record(event: ActivityInsert): Promise<ActivityEvent>
recent(limit?: number, beforeId?: number): Promise<ActivityEvent[]>
fills(limit?: number): Promise<ActivityEvent[]>
recordWalletTx(tx: Omit<WalletTx, "id" | "ts">): Promise<void>
walletTxs(limit?: number): Promise<WalletTx[]>
walletTxsWithoutAmounts(limit?: number): Promise<WalletTx[]>
updateWalletTx(id: number, patch: Pick<WalletTx, "token" | "amount" | "to" | "tokenIn" | "amountIn">): Promise<void>
orderIdsMissingSummary(limit?: number): Promise<string[]>
attachOrder(orderId: string, order: OrderSummary): Promise<ActivityEvent[]>
orderHistory(page: number, pageSize: number): Promise<OrderHistoryPage>
knowsOrder(orderId: string): Promise<boolean>
unsettledOrders(limit?: number): Promise<string[]>
retypeLegacyBid(orderId: string): Promise<ActivityEvent[]>
```

Observability rather than correctness: dropping a row costs a line in the activity view and nothing
else, so an implementation may prune, sample or cap history freely.

`ActivityEvent`: `id`, `ts`, `type` (`"detected" | "bid" | "filled" | "lost" | "executed" | "skipped" | "rebalance"`),
`orderId`, `chainId`, `strategy`, `success`, `reason`, `volumeUsd`, `profitUsd`, `txHash`, `order`
(an `OrderSummary` of the swap, or `null`).

### StateStore

```typescript lineNumbers
get(): Promise<RuntimeState>
set(state: RuntimeState): Promise<void>
patch?(patch: Partial<RuntimeState>): Promise<RuntimeState>
```

`RuntimeState` is `{ paused?: boolean }`.

`set` replaces the whole record. `patch` is optional and merges, leaving keys it does not name
untouched — implement it if your backend can do that atomically. The fallback when you do not is a
read, a merge and a write back, which loses a key another writer set in between.

### LimitOrderStore

```typescript lineNumbers
create(order: LimitOrderInsert): Promise<LimitOrder>
get(id: string): Promise<LimitOrder | null>
list(filter?: LimitOrderFilter): Promise<LimitOrder[]>
open(): Promise<LimitOrder[]>
setPosting(id: string, posting: LimitOrderPosting, only?: LimitOrderStatus[]): Promise<LimitOrder | null>
setStatus(id: string, status: LimitOrderStatus, lastError?: string | null, only?: LimitOrderStatus[]):
    Promise<LimitOrder | null>
reserve(id: string, amount: string): Promise<boolean>
release(id: string, amount: string): Promise<void>
drawDown(id: string, amount: string): Promise<LimitOrder | null>
recordFill(fill: LimitOrderFillInsert): Promise<void>
fills(limitOrderId: string, limit?: number): Promise<LimitOrderFill[]>
fillHistory(): Promise<LimitOrderFillRecord[]>
transaction<T>(settle: () => Promise<T>): Promise<T>
```

`fillHistory` returns every fill of every order, oldest first, each with its order's `book`, `base`,
`quote`, `side` and `price`. [`profitability()`](#profitabilityperiod-tzoffsetminutes) is worked
out from it, so a store that keeps `amountIn` on each fill gets exact figures.

### InventoryStore

```typescript lineNumbers
record(balances: Record<string, number>): Promise<void>
latest(): Promise<InventorySnapshot | null>
since(from: Date): Promise<InventorySnapshot[]>
```

What the solver held, as whole tokens per symbol, recorded about once a day. Profitability compares
a period's profit with the inventory it began with, and a snapshot that was never taken cannot be
recovered from the chain. `InventorySnapshot` is `id`, `takenAt` (SQLite-style UTC) and `balances`.
`since` returns snapshots oldest first. Losing a row costs a figure on the analytics page and
nothing else.

<Callout type="warn">
    Correctness-critical, like `BidStore`. `remaining` and `reserved` are inventory: they are what
    stop two chains paying out the same liability twice, so a store that loses writes overcommits
    real money.
</Callout>

`open()` is what the matcher prices against. `setPosting` and `setStatus` take an optional `only`
list and write only while the row still holds one of those statuses, answering `null` otherwise, so
a slow orderbook answer cannot undo a cancel or expiry that landed first. `reserve` adds a hold
only while the order is `open` and `remaining` covers that one hold. `drawDown` works the order down
by delivered output, floored at zero. `transaction` runs a fill's settlement — claim the bid's
holds, draw the order down, record the fill — as one unit where the backend can; the bundled SQLite
store keeps limit orders in the same database as bids for that reason.

### Implementations

| Class | Import from | Notes |
|------|-------------|-------|
| `MemoryDataStore` | `@hyperbridge/simplex` | Default. Process-local, row-capped, lost on exit |
| `SqliteDataStore` | `@hyperbridge/simplex/sqlite` | Durable. Built on `node:sqlite`, so nothing to install |

`SqliteDataStore(dataDir)` keeps `bids.db` and `activity.db` in the given directory, so a data
directory written by the binary is picked up unchanged. Limit orders and operator state ride in
`bids.db` beside the bids, and implements `patch`; a `runtime-state.json` from an earlier version is imported once
and then removed. It is built on Node's
built-in `node:sqlite`, so there is no native module to install or compile — which is why the
package requires Node 22.16 or newer.

**Example — a custom backend:**

```typescript lineNumbers
import type { SimplexDataStore } from "@hyperbridge/simplex"

const store: SimplexDataStore = {
    bids: new PostgresBidStore(pool),
    activity: new PostgresActivityStore(pool),
    state: new RedisStateStore(redis),
    limitOrders: new PostgresLimitOrderStore(pool),
    close: () => pool.end(),
}

const simplex = await Simplex.start({ config, data: store })
```

## Scanners

Scanning a chain is identical work for every solver — the `getLogs` filter carries no solver-specific
term — so N solvers pointed at one chain issue N copies of the same request stream. A scanner runs the
scan once and feeds every solver you hand it to.

Sharing is explicit. A solver started without a scanner builds a private one from its own config and
closes it on `stop()`; a scanner you build is yours, and `stop()` leaves it running.

### OrderScanner.create(options)

```typescript lineNumbers
static async create(options: {
    chains: ScannerChainConfig[]
    scanIntervalSecs?: number
    loggers?: LoggerContext
}): Promise<OrderScanner>
```

**Parameters:**

| Name | Type | Description |
|------|------|-------------|
| `options.chains` | `ScannerChainConfig[]` | Same shape as the config's `chains`, so it can be passed straight through |
| `options.chains[].rpcUrls` | `string[]` | Endpoints to scan with. Several enables quorum log scanning |
| `options.chains[].bundlerUrl` | `string` | Carried so a config array passes through unchanged; unused for scanning |
| `options.chains[].chainId` | `number` | Optional. Read back from the endpoints when omitted |
| `options.chains[].gateway` | `HexString` | Optional. Taken from the SDK chain registry when omitted |
| `options.scanIntervalSecs` | `number` | Optional. Seconds between scans of each chain. Defaults to 3, the same default `blockScanIntervalSeconds` carries. Minimum 0.1 |

**Throws:** if an endpoint set is invalid or unreachable, if two entries resolve to the same chain, or if `scanIntervalSecs` is below 0.1.

### OrderScanner methods

```typescript lineNumbers
subscribe(handlers: OrderScannerHandlers): Subscription
chains(): number[]
addChain(chain: ScannerChainConfig): Promise<number>
setRpcUrls(chainId: number, rpcUrls: string[]): Promise<void>
removeChain(chainId: number): Promise<void>
close(): Promise<void>
```

A subscription receives events for **every** chain in the scanner, so subscribers match on
`event.chainId` — a shared scanner may carry more chains than a given solver wants.

`setRpcUrls` probes the new endpoints and rejects them unless they answer for the chain being edited,
then swaps them in **keeping that chain's block cursor** — so an endpoint change leaves no unscanned
gap. It throws on a chain the scanner does not have.

| Handler | Payload |
|---------|---------|
| `onOrder` | `ScannedOrder` — `{ order, transactionHash, blockNumber, blockHash, logIndex, chain, chainId }` |
| `onFill` | `ScannedFill` — `{ commitment, filler, chainId, blockNumber, blockHash, logIndex }` |
| `onError` | `(error, chainId)` — informational; the scanner retries and never advances its cursor past an unread range |

`Subscription` is `{ close(): void; readonly dropped: number }`.

<Callout type="warn">
    Delivery is at-least-once and per-chain FIFO. A scanner that resumes from a cursor after a
    reconnect re-delivers, so subscribers de-duplicate on `order.id`. A scanner also never blocks on
    a slow subscriber — that would stall every other solver reading it — so one that falls behind
    loses its oldest events and counts them in `dropped`.
</Callout>

Every `ScannedFill` reaches every subscriber: `filler` is `indexed: false` on both `OrderFilled` and
`PartialFill`, so it can never be narrowed to a topic filter.

### Scanner ownership

`chains.add` and `chains.setRpcUrls` edit a scanner the solver built for itself, and throw on one you
supplied — repointing endpoints under the other solvers reading it would be action at a distance.
Manage a shared scanner through the scanner.

`chains.remove` does **not** throw on a supplied scanner: it stops this solver from matching the
chain and leaves the shared scan loop running for everyone else, which is the correct outcome for a
scanner you own.

## Logging

The library is **silent until a sink is registered**. Importing the package does not write to stdout,
install a formatter, or spawn a transport worker.

```typescript lineNumbers
interface LogSink {
    write(line: string): void
}
```

Node's `Writable` satisfies it, so `process.stdout`, a file stream, a socket or a `pino-pretty`
transform all work as-is, as does an object literal that forwards into your own logger.

### simplex.addLogSink(sink)

Adds another destination for **this solver's** records and returns a function that removes it.
Other instances are unaffected.

```typescript lineNumbers
addLogSink(sink: LogSink): () => void
```

### addLogSink(sink)

The module-level function registers on the process-wide fallback context instead. A running solver
logs to its own context and the validators throw rather than log; the one library path that writes
to the fallback is a shared scanner built without a `loggers` option.

```typescript lineNumbers
addLogSink(sink: LogSink): () => void
```

**Example:**

```typescript lineNumbers
import { addLogSink, configureLogger } from "@hyperbridge/simplex"

const detach = addLogSink({ write: (line) => myLogger.write(JSON.parse(line)) })
configureLogger("debug")
// ...
detach()
```

### configureLogger(level)

Sets verbosity on the process-wide fallback context. Does not affect running solvers — use
`simplex.setLogLevel` for those.

```typescript lineNumbers
configureLogger(level: LogLevel): void
```

### LoggerContext

An isolated destination: its own sinks, level and pino instance. Each `Simplex` constructs one from
`SimplexOptions.logger`, which is what keeps two solvers' records apart. Construct one directly only
if you want to share a destination across something the solver does not own.

```typescript lineNumbers
new LoggerContext(options?: { level?: LogLevel; sink?: LogSink })
addSink(sink: LogSink): () => void
setLevel(level: LogLevel): void
get(module?: string): Logger
```

### getLogger(module?)

Returns a logger with `trace`, `debug`, `info`, `warn`, `error` and `fatal`, each taking pino's
`(obj, msg)` or `(msg)` shape. Records are tagged with `moduleTag`.

```typescript lineNumbers
getLogger(module?: string | { module?: string }): Logger
```

<Callout type="info">
    Logging is scoped per solver. Two `Simplex` instances in one process write to their own sinks at
    their own levels — `solverA.setLogLevel("debug")` leaves `solverB` alone.
</Callout>

## Validators

All pure — no I/O, and they run the same rules boot applies, so a config that passes here starts.
Useful for gating input from a form, a database or an API before committing to a start.

| Function | Purpose |
|----------|---------|
| `validateConfig(config, cliWatchOnly?)` | The full config |
| `validatePairConfigs(pairs, userAssets?)` | A non-empty `pairs` array against the asset table: no duplicate or reversed market, every symbol known |
| `validateAssetDefinitions(assets)` | Custom asset entries |
| `assertConfirmationCoverage(policies, chainIds)` | Every configured chain has a confirmation curve |
| `validateVaultToml(vaults)` | Vault treasury entries; takes the array, not one entry |
| `pickAnchorStable(pairs, symbol)` | The first USD stable with no market against a symbol yet, or `null` |
| `normalizeSymbol(symbol)` | Trimmed, uppercased |
| `isRegistrySymbol(symbol)` / `registrySymbols()` | Built-in registry membership |
| `parseChainKey(key)` / `formatChainKey(id)` | `"EVM-1"` ↔ `1` |

`validateConfig` requires an `orderbook` section with a `url`, and checks `defaultTtlSecs` (at least
900), `reconcileIntervalSecs` and `requestTimeoutMs` are positive integers. Limit orders are not
config and are validated by `limitOrders.create` against the live orderbook.

`USD_STABLE_SYMBOLS` is the set of symbols pegged to one dollar. Confirmation depth is sized in USD,
and a token's USD value is derived from these stables through the rates of the operator's open
limit orders.

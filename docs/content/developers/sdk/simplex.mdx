# Simplex

[Simplex](/developers/evm/intent-gateway/simplex) is an automated solver for the Intent Gateway. It
ships as a binary, and as `@hyperbridge/simplex` — the same engine, running inside your own process.
No TOML file, no separate service, and every runtime control the web dashboard offers is a method on
the object you get back.

Reach for the library when the solver is one component of a larger system: you already have a
database, a dashboard, an alerting pipeline, or pricing logic that needs to move curves as the market
does. If you just want a solver running, the [binary](/developers/evm/intent-gateway/simplex) is
less work.

```bash lineNumbers
npm install @hyperbridge/simplex
```

Node.js 22 or later. The package ships ESM and CJS builds with bundled types.

## Starting a solver

`Simplex.start` takes a plain config object and returns once the solver is running: chains resolved,
EIP-7702 delegation in place where solver selection is active, scanners live.

```ts lineNumbers
import {
    Simplex,
    privateKeySigner,
    type SimplexConfig,
} from "@hyperbridge/simplex"

const config: SimplexConfig = {
    simplex: {
        maxConcurrentOrders: 5,
        // Seconds between block scans per chain. Defaults to 3, minimum 0.1.
        blockScanIntervalSeconds: 3,
        substratePrivateKey: process.env.SUBSTRATE_KEY!,
        hyperbridgeWsUrl: "wss://hyperbridge-mainnet-rpc.blockops.network",
    },
    chains: [
        {
            rpcUrls: ["https://base.example"],
            bundlerUrl: "https://bundler.example/base",
        },
        {
            rpcUrls: ["https://arbitrum.example"],
            bundlerUrl: "https://bundler.example/arb",
        },
    ],
    pairs: [
        {
            token0: "USDC",
            token1: "USDC",
            maxOrderSize: "5000",
            // Same-asset market: ask-only, strictly below par.
            // The gap to 1 is your spread.
            askPriceCurve: [{ amount: "0", price: "0.9995" }],
        },
    ],
}

const simplex = await Simplex.start({
    config,
    signer: privateKeySigner(process.env.SOLVER_KEY as `0x${string}`),
})
```

`start` rejects if the config is invalid, a chain's RPCs are unreachable, or delegation fails on
every chain. It never returns a half-started solver, so there is no "is it ready yet" state to poll.

Stop it with `await simplex.stop()` — idempotent, drains in-flight fills, unwinds any vault position
marked `redeemOnShutdown`, and never calls `process.exit`.

<Callout type="warn">
    The config object is the shape the binary's `filler-config.toml` parses into, minus
    `[simplex.signer]` — signing is an argument, not config. The
    [configuration reference](/developers/evm/intent-gateway/simplex#configuration) documents every
    other field; read the TOML tables there as object keys.
</Callout>

## Signing

Signing is pluggable. `Signer` is the interface; `privateKeySigner`, `turnkeySigner` and
`mpcVaultSigner` are implementations of it, and so is anything you write.

```ts lineNumbers
interface Signer {
    /** The address every fill, bid and delegation is attributed to. */
    address: HexString
    /** Names the backend in logs. */
    mode: string

    /** EIP-712. Signs every bid UserOperation and every paymaster permit. */
    signTypedData(typedData: TypedDataPayload): Promise<HexString>
    /** The EIP-7702 delegation that makes this account a solver. */
    signAuthorization(auth: AuthorizationRequest): Promise<Signature>
    /** Returns the signed, RLP-encoded transaction, ready to broadcast. */
    signTransaction(tx: SignerTransaction): Promise<HexString>
}
```

Three operations and an identity. Each names *what* is being authorised — a typed-data payload, an
EIP-7702 authorization, a transaction — rather than handing over a digest, so a custody provider's
policy engine can read what it is about to sign. Nothing on the interface is a viem type, so
satisfying it never means matching this package's viem version.

There is no chain id parameter on `signTypedData`: EIP-712 carries it in `domain.chainId`, which is
what the digest covers and what a backend that scopes a signing request to a chain reads.

<Callout type="warn">
    Any EIP-712 payload you build must list `EIP712Domain` in `types`. viem ignores it when hashing
    locally, so a payload without it looks correct against a private key — but MPCVault and Turnkey
    both hash from the JSON they are sent and derive the domain type from that entry. Without it
    they sign a different digest than your verifier checks, and the failure is quiet: the signature
    is well-formed and recovers to an address that is not yours.
</Callout>

A solver needs a signer unless every chain is watch-only, where it signs nothing and a throwaway key
stands in.

Each method returns something different, and the difference is the part that trips an implementation:

| Method | Return exactly |
|--------|----------------|
| `signTypedData` | The 65-byte `r ‖ s ‖ v` signature as 0x-hex (132 characters), `v` **27 or 28** — what `eth_signTypedData_v4` and viem's `signTypedData` produce. On-chain validation recovers against this form |
| `signAuthorization` | The **split** signature `{ r, s, yParity }`: `r`/`s` as 32-byte 0x-hex, `yParity` strictly **0 or 1** (subtract 27 from a legacy `v` — anything else is rejected, because EIP-7702 would otherwise skip the mis-encoded tuple silently). Split because the authorization is embedded field-by-field in the transaction |
| `signTransaction` | The **whole signed transaction** — typed-envelope RLP as `eth_sendRawTransaction` takes it (`0x02…` for EIP-1559, `0x04…` for set-code), not a bare signature. From a signed digest, viem's `serializeTransaction(tx, signature)` produces it |


### Out of the box

```ts lineNumbers
import {
    privateKeySigner,
    turnkeySigner,
    mpcVaultSigner,
} from "@hyperbridge/simplex"

// A raw key in this process.
const local = privateKeySigner(process.env.SOLVER_KEY as `0x${string}`)

// Turnkey. Async — it fetches the account on creation.
const turnkey = await turnkeySigner({
    organizationId: process.env.TURNKEY_ORG_ID!,
    apiPublicKey: process.env.TURNKEY_API_PUBLIC_KEY!,
    apiPrivateKey: process.env.TURNKEY_API_PRIVATE_KEY!,
    // Any Ethereum address in your Turnkey wallet.
    signWith: process.env.TURNKEY_SIGN_WITH!,
})

// MPCVault. Needs a running client-signer container.
const mpc = mpcVaultSigner({
    apiToken: process.env.MPCVAULT_API_TOKEN!,
    vaultUuid: process.env.MPCVAULT_VAULT_UUID!,
    accountAddress: process.env.MPCVAULT_ADDRESS as `0x${string}`,
    callbackClientSignerPublicKey: process.env.MPCVAULT_CALLBACK_KEY!,
})
```

Turnkey signs transactions and EIP-7702 authorizations through its own structured encodings, so its
policy engine sees both. MPCVault signs transactions through its vault API, and hashes the
authorization tuple itself since it has no structured encoding for one. Neither has privileged
access to the solver; a signer you write can do the same things.

### Anything that speaks viem

`viemSigner` adapts a viem local account, carrying each operation through to the account's own
implementation:

```ts lineNumbers
import { viemSigner } from "@hyperbridge/simplex"

const signer = viemSigner(await someProvider.getAccount())
```

viem makes `signAuthorization` optional on an account; the interface does not, so the adapter falls
back to hashing the tuple and signing it with `sign`. An account with neither cannot delegate, and a
solver that cannot delegate cannot bid, so that is rejected at construction rather than at the first
fill.

### A backend that only signs digests

An HSM, a KMS or a remote signer that exposes nothing but `sign(hash)` does not implement the
interface by hand — `digestSigner` does the hashing and the RLP for you:

```ts lineNumbers
import { digestSigner } from "@hyperbridge/simplex"

const signer = digestSigner({
    address: await hsm.address(),
    mode: "hsm",
    // Must resolve to { r, s, yParity } with yParity 0 or 1 — split a 65-byte
    // hex signature with viem's parseSignature. A backend handing back the
    // legacy v (27/28) is rejected rather than mis-encoded.
    sign: async (hash) => parseSignature(await hsm.sign(hash)),
})
```

That keeps transaction serialisation and EIP-7702 authorization hashing in one tested place instead
of in every integration. The trade is visibility: your provider sees 32 bytes, not the transaction.
If it can do better, implement `Signer` directly.

### Writing one from scratch

Implement `Signer` when your backend can see structure and you want it to. Each method owns its
encoding: return a 65-byte signature for the typed data, split components for the authorization, and
signed RLP bytes for the transaction.

```ts lineNumbers
const signer: Signer = {
    address: await vault.address(),
    mode: "vault",
    signTypedData: (payload) => vault.signTypedData(payload),
    signAuthorization: (auth) => vault.signDelegation(auth),
    signTransaction: (tx) => vault.signTransaction(tx),
}
```

A signer is also the natural place for the policy your provider cannot express: rate limits, a
per-chain kill switch, an approval queue, an audit log of everything the solver ever asked to be
signed.

```ts lineNumbers
const audited: Signer = {
    ...base,
    mode: "audited",
    signTransaction: async (tx) => {
        await audit.record({ chainId: tx.chainId, to: tx.to, value: tx.value })
        return base.signTransaction(tx)
    },
}
```

<Callout type="info">
    `SimplexConfig` has no signer field at all — the binary's `[simplex.signer]` block lives on
    `FillerConfigFile`, the on-disk shape. Loading one of those files yourself?
    `createSigner(config.simplex.signer)` builds the signer it describes. `Simplex.start` will not
    read the block for you: passing a parsed file with no `signer` throws, rather than quietly
    picking a key you did not pass.
</Callout>

## Persistence

Simplex remembers three things across a restart: the bids it submitted, its activity feed, and
whether the operator paused it. That lives behind the `SimplexDataStore` interface.

The default is in-memory and lost on exit, which is fine for tests and watch-only observers. **A
solver that submits bids needs a durable store** — a successful bid locks a deposit on Hyperbridge
that is only reclaimable by retracting it, and the retraction sweep finds what to reclaim by
querying the bid store. Lose those records and you leak deposits.

The bundled SQLite store is a separate entry point, so nothing native is loaded unless you import
it. `better-sqlite3` is an optional dependency — installed by default, but free to fail to build
without breaking the package:

```ts lineNumbers
import { SqliteDataStore } from "@hyperbridge/simplex/sqlite"

const simplex = await Simplex.start({
    config,
    data: new SqliteDataStore("./simplex-data"),
})
```

To use your own backend — Postgres, Redis, a hosted API — implement the interface:

```ts lineNumbers
import type { SimplexDataStore } from "@hyperbridge/simplex"

const store: SimplexDataStore = {
    // store, byCommitment, expiredUnretracted, markRetracted, markDead, …
    bids: myBidStore,
    // record, recent, fills, recordWalletTx, walletTxs
    activity: myActivityLog,
    // get, set
    state: myStateStore,
}
```

Every method is async. Only `bids` is correctness-critical: `store` must be durable before it
resolves. `activity` is observability — prune, sample or cap it freely.

## Reacting to orders

The solver emits a typed event for everything it does.

```ts lineNumbers
simplex.on("order:detected", ({ order, transactionHash }) => { /* … */ })
simplex.on("order:skipped", ({ orderId, reason }) => { /* … */ })
simplex.on("order:filled", ({ orderId, txHash, volumeUsd, profitUsd }) => {
    /* … */
})
simplex.on("order:executed", ({ orderId, success, strategy, error }) => {
    /* … */
})
simplex.on("order:timing", ({ orderId, phase, durationSec }) => { /* … */ })
simplex.on("rebalance", ({ success, transferCount, executedCount }) => {
    /* … */
})
// Every row written to the activity store.
simplex.on("activity", (event) => {
    /* … */
})
```

Payloads are inferred from the event name, so a wrong field is a compile error. A misspelled event
name is not — the catch-all overload that keeps `EventEmitter` compatible accepts any string. These
events are the whole telemetry surface: counters, dashboards and alerting are yours to build on
them, with nothing privileged left inside.

## Changing things while it runs

Every mutation applies to the live solver and binds on the next order. Nothing here needs a restart.

### Pairs

```ts lineNumbers
simplex.pairs.list()

// Pair 0 above is the same-token USDC/USDC market: ask-only, strictly
// below par. Widen its spread to 10 bps.
await simplex.pairs.setCurve(0, "ask", [{ amount: "0", price: "0.999" }])
await simplex.pairs.setMaxOrderSize(0, "10000")

// Open a cross-asset market — it lands at index 1.
await simplex.pairs.add({
    token0: "USDC",
    token1: "CNGN",
    maxOrderSize: "5000",
    // Both curves are CNGN per USDC. Bid is the solver buying CNGN, so it
    // wants more CNGN per USDC; ask is selling, so it wants to give fewer.
    // An uncrossed book therefore has bid ABOVE ask — the gap is the spread.
    bidPriceCurve: [{ amount: "0", price: "1550" }],
    askPriceCurve: [{ amount: "0", price: "1545" }],
})

// One-sided LP: stop buying CNGN, keep selling it.
await simplex.pairs.clearCurve(1, "bid")
```

`setCurve` mutates the policy instance the engine prices with, so the new curve is live on the next
evaluation. `pairs.remove(index)` closes a market; indices shift down, so remove from the highest
index first if you are closing several. New pairs are validated against the same rules boot applies — a pair accepted here is
one a restart would also accept.

Repricing from a market feed is the common case:

```ts lineNumbers
// Pair 1 is the cross-asset market added above — two-sided, so both
// curves apply. A same-token pair takes an ask curve only.
feed.on("tick", async ({ mid }) => {
    const bid = (mid * 1.001).toFixed(4)
    const ask = (mid * 0.999).toFixed(4)
    await simplex.pairs.setCurve(1, "bid", [{ amount: "0", price: bid }])
    await simplex.pairs.setCurve(1, "ask", [{ amount: "0", price: ask }])
})
```

### Chains

```ts lineNumbers
await simplex.chains.add({
    rpcUrls: ["https://polygon.example"],
    bundlerUrl: "https://bundler.example/polygon",
    // Required for chains with no built-in confirmation curve.
    confirmationPolicy: {
        points: [
            { amount: "1000", value: 2 },
            { amount: "100000", value: 32 },
        ],
    },
})

await simplex.chains.setRpcUrls(8453, ["https://base-new.example"])
await simplex.chains.setWatchOnly(8453, true)
await simplex.chains.remove(137)
```

`add` probes the endpoints and reads the chain id back from them before mutating anything, so a
wrong or unreachable RPC is rejected rather than half-applied. `setRpcUrls` swaps the scan loop's
endpoints while keeping its block cursor, so the change leaves no gap in the scanned range. `remove`
drains in-flight fills first, then stops scanning the chain.

### Vaults, assets, rebalancing

```ts lineNumbers
// Validate against chain state, change nothing.
await simplex.vaults.preflight(vaults)
await simplex.vaults.set(vaults)
await simplex.vaults.sweepNow()
await simplex.vaults.redeemAll()

await simplex.assets.add({ BRZ: { "EVM-137": "0x…" } })
simplex.assets.resolve("USDC", "EVM-8453")

// Requires `rebalancing` in the boot config; on a solver started without
// it, `set` throws rather than conjuring a rebalancer mid-flight.
await simplex.rebalancing.set({
    // A fraction, not a percentage: rebalance once the balance falls to
    // (1 - triggerPercentage) x base, so 0.2 triggers at 80% of base.
    triggerPercentage: 0.2,
    // Keyed by numeric chain id as a string, not the state machine id.
    baseBalances: { USDC: { "8453": "10000" } },
})
await simplex.rebalancing.trigger()
```

### Wallet and lifecycle

```ts lineNumbers
simplex.wallet.address
simplex.wallet.balances()
await simplex.wallet.send({
    chain: "EVM-8453",
    token: "0x…",
    amount: "100",
    to: "0x…",
})
await simplex.wallet.history()

// Stop filling; monitoring continues, and the pause survives a restart.
await simplex.pause()
await simplex.resume()
simplex.status()
await simplex.activity()
await simplex.bidStats()   // watch `pendingRetraction`: deposits still locked
```

## Persisting runtime edits

Mutations update the live config object, so `simplex.config()` always reflects what is actually
running. Pass `onConfigChange` to persist it however you like:

```ts lineNumbers
const simplex = await Simplex.start({
    config,
    data: new SqliteDataStore("./simplex-data"),
    onConfigChange: async (config) => {
        await db.settings.put("filler-config", config)
    },
})
```

Without it, edits apply live but do not survive a restart — `configPath` alone does not persist them;
it is informational. The binary persists its own edits by a different route — its dashboard writes
the TOML file directly — so `onConfigChange` is the library's equivalent, not a wrapper around it.

## Multiple Simplex Instances

Instances share no state, so several solvers can run in one process — different keys, different
chains, different books:

```ts lineNumbers
const [solverA, solverB] = await Promise.all([
    Simplex.start({
        config: configA,
        data: new SqliteDataStore("./data/solver-a"),
    }),
    Simplex.start({
        config: configB,
        data: new SqliteDataStore("./data/solver-b"),
    }),
])
```

Give each its own data directory. Two solvers sharing one bid store would each see the other's bids
as theirs to retract.

Started like that, each solver scans the chains itself. Two solvers watching Base issue two
identical `getLogs` streams forever, because the filter carries nothing solver-specific — so at any
real fleet size the scanning, not the filling, is what exhausts an RPC quota.

### Singleton Scanners

Build one `OrderScanner` and one `HyperbridgeScanner` and hand them to every solver that should
share them. The scan runs once, and each solver receives every event:

```ts lineNumbers
import { Simplex, OrderScanner, HyperbridgeScanner } from "@hyperbridge/simplex"

const orders = await OrderScanner.create({ chains: config.chains })
const hyperbridge = await HyperbridgeScanner.create(
    config.simplex.hyperbridgeWsUrl,
)

const solverA = await Simplex.start({
    config: configA,
    orderScanner: orders,
    hyperbridgeScanner: hyperbridge,
})
const solverB = await Simplex.start({
    config: configB,
    orderScanner: orders,
    hyperbridgeScanner: hyperbridge,
})

// Yours to close, whenever both solvers are done with it.
await orders.close()
await hyperbridge.close()
```

`chains` takes the same array as your config's, so it can be passed straight through. The scanner
polls every 3 seconds by default; `scanIntervalSecs` changes that, with the same 0.1 minimum the
TOML validator applies. A solver that builds its own scanner reads the interval from
`config.simplex.blockScanIntervalSeconds` instead — one you supply keeps whatever interval you gave
it, since the solvers reading it may disagree:

```ts lineNumbers
const orders = await OrderScanner.create({
    chains: config.chains,
    scanIntervalSecs: 0.5,
})
```
 Entries without a `chainId` have it read back from the first endpoint listed, which also proves
that endpoint answers before a solver depends on it.

`HyperbridgeScanner` carries phantom orders — the quote requests solvers respond to, which is how
Hyperbridge indexes prices. One poll feeds every solver reading it.

A scanner you build is yours. Solvers subscribe and unsubscribe; none of them closes it, and a
solver's `stop()` leaves it running for whoever else is reading.

<Callout type="info">
    Omit both and a solver builds private scanners from its own config and closes them on `stop()`.
    Nothing is ever shared implicitly — sharing is something you do on purpose.
</Callout>

### Scanner Management

A shared scanner is edited through the scanner, so every solver reading it sees the same events:

```ts lineNumbers
// Start scanning a chain. Solvers still opt in individually — see below.
await orders.addChain({
    rpcUrls: ["https://polygon.example"],
    bundlerUrl: "https://bundler.example/polygon",
})

// Swap endpoints. The cursor is kept, so no block goes unscanned.
await orders.setRpcUrls(8453, ["https://base-new.example"])

// Stop scanning one, then list what is left.
await orders.removeChain(137)
orders.chains() // [8453]
```

`addChain` reads the chain id back from the endpoints when you omit it, and rejects a chain the
scanner already has. `setRpcUrls` checks the new endpoints answer for that same chain before
swapping them in. `removeChain` stops that scan loop; subscribers simply stop seeing the chain.

Adding a chain to the scanner does **not** by itself put a solver to work on it. Each solver
matches incoming events against its own configured chains, so tell it separately — the scanner
supplies the events, the solver decides which it wants:

```ts lineNumbers
await orders.addChain({ rpcUrls, bundlerUrl })   // the scanner sees it
await solverA.chains.add({ rpcUrls, bundlerUrl }) // this solver acts on it
```

`simplex.chains.add` and `.setRpcUrls` only reach a scanner that solver built for itself. On one you
supplied they throw rather than repoint endpoints underneath the other solvers reading it:

> Endpoints for chain 8453 belong to the order scanner you supplied — change them there, so the
> other solvers reading it are not repointed underneath them.

## Logging

**The library writes nothing anywhere until you tell it where.** Importing
`@hyperbridge/simplex` does not touch your stdout, install a formatter, or spawn a transport worker —
a library has no business logging into a host process uninvited.

Point `logger` at any sink: it receives one NDJSON record per line, and anything Writable-shaped
works.

```ts lineNumbers
import { createWriteStream } from "node:fs"

const simplex = await Simplex.start({
    config,
    logger: createWriteStream("solver.log", { flags: "a" }),
})
```

Forwarding into a logger you already have is the same shape:

```ts lineNumbers
const simplex = await Simplex.start({
    config,
    logger: { write: (line) => myLogger.write(JSON.parse(line)) },
})
```

Or hand it `process.stdout` if you do want it on the console:

```ts lineNumbers
const simplex = await Simplex.start({
    config,
    logger: process.stdout,
})
// {"level":30,"time":1755151200000,"moduleTag":"[simplex]","msg":"..."}
```

That prints raw NDJSON, one record per line. For the binary's colourised output, pipe through
`pino-pretty` yourself — formatting is a presentation choice that belongs to your application,
not to this package.

Set verbosity with `config.simplex.logging`, or `simplex.setLogLevel("warn")` on a running solver,
which applies immediately including to services already constructed. Level alone produces no output;
a sink is still required.

Logging is scoped to the solver, not the process. Each `Simplex` owns its own destination and level,
so several solvers in one process keep their records apart:

```ts lineNumbers
const [solverA, solverB] = await Promise.all([
    Simplex.start({ config: configA, logger: logA }),
    Simplex.start({ config: configB, logger: logB }),
])

solverA.setLogLevel("debug")      // solverB stays at its own level
solverA.addLogSink(auditStream)   // and its own sinks
```

`addLogSink(sink)` at module level registers a destination on the process-wide fallback context. A
running solver logs only to its own context — the one thing that writes to the fallback is a shared
scanner built without a `loggers` option, so pass one there if you route scanner output somewhere
specific.

## Validating a config without starting

The validators are pure and run the same rules boot does, so you can gate a config — from a form, a
database, an API — before committing to a start:

```ts lineNumbers
import {
    validateConfig,
    validatePairConfigs,
    bookCrossedAt,
} from "@hyperbridge/simplex"

// Both throw with a descriptive message.
validateConfig(config)
validatePairConfigs(config.pairs!, config.assets, false)

// A crossed book is legal but means a full round trip loses money —
// worth warning on.
const crossed = bookCrossedAt(pair.bidPriceCurve!, pair.askPriceCurve!)
if (crossed) console.warn(`book crosses at ${crossed.amount}`)
```

# Intent gateway order cancellation (OrderCancelled to EscrowRefunded)

1. `IntentGatewayV2.cancelOrder` emits `OrderCancelled(commitment, canceller)` before branching into same-chain, source-chain, or destination-chain cancellation. Later checks can revert; a revert discards the log. The event is emitted on the chain where cancellation begins, and `canceller` is the caller, which may differ from the creator on the permissionless destination route.
2. `handleOrderCancelledEventV3` resolves the event timestamp and calls `IntentGatewayV3Service.recordOrderCancellation`. It creates an `IOrderV3Cancellation` row identified by `{transactionHash}.{logIndex}` so repeated cancellation attempts remain visible.
3. For any indexed parent, the service saves `CANCELLED` in `IOrderV3StatusMetadata`. It never saves the parent `IOrderV3` row, so a cancellation indexer's stale cache cannot overwrite a source-chain refund. The event relation exposes all cancellation logs; metadata uses the established `{commitment}.{status}` ID.
4. A same-chain cancellation emits `EscrowRefunded` later in the same transaction. A cross-chain cancellation starts messaging and does not establish a refund by itself. The existing refund handler sets the parent to `REFUNDED` when the source-chain refund is observed. Until then, cancellation alone leaves the parent's previous status intact.
5. If the order has not been indexed yet, cancellation writes `PendingStatusMetadata` directly. The existing placement or periodic pending-status flush copies this into order metadata and removes the pending record, without changing the parent's status. The cancellation event itself remains available before its parent is indexed.
6. Clients use the cancellation relation or status metadata to detect initiation. A `status: CANCELLED` parent filter does not identify these orders. A terminal status takes precedence over cancellation metadata even when chain timestamps or arrival order put cancellation last.

# Simplex

[Simplex](/developers/evm/intent-gateway/simplex) is an automated solver for the Intent Gateway. It
ships as a binary, and as `@hyperbridge/simplex` — the same engine, running inside your own process.
No TOML file, no separate service, and every runtime control the web dashboard offers is a method on
the object you get back.

Reach for the library when the solver is one component of a larger system: you already have a
database, a dashboard, an alerting pipeline, or pricing logic that needs to move curves as the market
does. If you just want a solver running, the [binary](/developers/evm/intent-gateway/simplex) is
less work.

```bash
npm install @hyperbridge/simplex
```

Node.js 22 or later. The package ships ESM and CJS builds with bundled types.

## Starting a solver

`Simplex.start` takes a plain config object and returns once the solver is running: chains resolved,
EIP-7702 delegation in place where solver selection is active, scanners live.

```ts
import { Simplex, SignerType, type SimplexConfig } from "@hyperbridge/simplex"

const config: SimplexConfig = {
    simplex: {
        signer: { type: SignerType.PrivateKey, key: process.env.SOLVER_KEY as `0x${string}` },
        maxConcurrentOrders: 5,
        queue: { maxRechecks: 10, recheckDelayMs: 30_000 },
        substratePrivateKey: process.env.SUBSTRATE_KEY!,
        hyperbridgeWsUrl: "wss://hyperbridge-mainnet-rpc.blockops.network",
    },
    chains: [
        { rpcUrls: ["https://base.example"], bundlerUrl: "https://bundler.example/base" },
        { rpcUrls: ["https://arbitrum.example"], bundlerUrl: "https://bundler.example/arb" },
    ],
    pairs: [
        {
            token0: "USDC",
            token1: "USDC",
            maxOrderSize: "5000",
            // Same-asset market: ask-only, strictly below par. The gap to 1 is your spread.
            askPriceCurve: [{ amount: "0", price: "0.9995" }],
        },
    ],
}

const simplex = await Simplex.start({ config })
```

`start` rejects if the config is invalid, a chain's RPCs are unreachable, or delegation fails on
every chain. It never returns a half-started solver, so there is no "is it ready yet" state to poll.

Stop it with `await simplex.stop()` — idempotent, drains in-flight fills, unwinds any vault position
marked `redeemOnShutdown`, and never calls `process.exit`.

<Callout type="warn">
    The config object is the same shape the binary's `filler-config.toml` parses into. The
    [configuration reference](/developers/evm/intent-gateway/simplex#configuration) documents every field;
    read the TOML tables there as object keys.
</Callout>

## Persistence

Simplex remembers three things across a restart: the bids it submitted, its activity feed, and
whether the operator paused it. That lives behind the `SimplexDataStore` interface.

The default is in-memory and lost on exit, which is fine for tests and watch-only observers. **A
solver that submits bids needs a durable store** — a successful bid locks a deposit on Hyperbridge
that is only reclaimable by retracting it, and the retraction sweep finds what to reclaim by
querying the bid store. Lose those records and you leak deposits.

The bundled SQLite store is a separate entry point, so the default install pulls in no native
modules:

```ts
import { SqliteDataStore } from "@hyperbridge/simplex/sqlite"

const simplex = await Simplex.start({
    config,
    data: new SqliteDataStore("./simplex-data"),
})
```

To use your own backend — Postgres, Redis, a hosted API — implement the interface:

```ts
import type { SimplexDataStore } from "@hyperbridge/simplex"

const store: SimplexDataStore = {
    bids: myBidStore,        // store, byCommitment, expiredUnretracted, markRetracted, markDead, …
    activity: myActivityLog, // record, recent, fills, recordWalletTx, walletTxs
    state: myStateStore,     // get, set
}
```

Every method is async. Only `bids` is correctness-critical: `store` must be durable before it
resolves. `activity` is observability — prune, sample or cap it freely.

## Reacting to orders

The solver emits a typed event for everything it does.

```ts
simplex.on("order:detected", ({ order, transactionHash }) => { /* … */ })
simplex.on("order:skipped", ({ orderId, reason }) => { /* … */ })
simplex.on("order:filled", ({ orderId, txHash, chainId, volumeUsd, profitUsd }) => { /* … */ })
simplex.on("order:executed", ({ orderId, success, strategy, commitment, error }) => { /* … */ })
simplex.on("order:timing", ({ orderId, phase, durationSec }) => { /* … */ })
simplex.on("rebalance", ({ success, transferCount, executedCount }) => { /* … */ })
simplex.on("activity", (event) => { /* every row written to the activity store */ })
```

Payloads are inferred from the event name, so a typo or a wrong field is a compile error. This is
the whole telemetry surface — the binary's Prometheus exporter is built on these same events, with
no privileged access.

## Changing things while it runs

Every mutation applies to the live solver and binds on the next order. Nothing here needs a restart.

### Pairs

```ts
simplex.pairs.list()
await simplex.pairs.setCurve(0, "ask", [{ amount: "0", price: "1550" }])
await simplex.pairs.setMaxOrderSize(0, "10000")
await simplex.pairs.clearCurve(0, "bid")          // one-sided LP: stop buying token1
await simplex.pairs.add({ token0: "USDC", token1: "CNGN", maxOrderSize: "5000",
                          askPriceCurve: [{ amount: "0", price: "1550" }] })
await simplex.pairs.remove(1)
```

`setCurve` mutates the policy instance the engine prices with, so the new curve is live on the next
evaluation. New pairs are validated against the same rules boot applies — a pair accepted here is
one a restart would also accept.

Repricing from a market feed is the common case:

```ts
feed.on("tick", async ({ mid }) => {
    await simplex.pairs.setCurve(0, "bid", [{ amount: "0", price: (mid * 0.999).toFixed(4) }])
    await simplex.pairs.setCurve(0, "ask", [{ amount: "0", price: (mid * 1.001).toFixed(4) }])
})
```

### Chains

```ts
await simplex.chains.add({
    rpcUrls: ["https://polygon.example"],
    bundlerUrl: "https://bundler.example/polygon",
    // Required for chains with no built-in confirmation curve.
    confirmationPolicy: { points: [{ amount: "1000", value: 2 }, { amount: "100000", value: 32 }] },
})

await simplex.chains.setRpcUrls(8453, ["https://base-new.example"])
await simplex.chains.setWatchOnly(8453, true)
await simplex.chains.remove(137)
```

`add` probes the endpoints and reads the chain id back from them before mutating anything, so a
wrong or unreachable RPC is rejected rather than half-applied. `setRpcUrls` rebuilds the chain's
scanner from its existing cursor, so the swap leaves no gap in the scanned block range. `remove`
stops the scanner first, then drains in-flight fills before dropping the chain.

### Vaults, assets, rebalancing

```ts
await simplex.vaults.preflight(vaults)   // validate against chain state, change nothing
await simplex.vaults.set(vaults)
await simplex.vaults.sweepNow()
await simplex.vaults.redeemAll()

await simplex.assets.add({ BRZ: { "EVM-137": "0x…" } })
simplex.assets.resolve("USDC", "EVM-8453")

await simplex.rebalancing.set({ triggerPercentage: 20, baseBalances: { USDC: { "EVM-8453": "10000" } } })
await simplex.rebalancing.trigger()
```

### Wallet and lifecycle

```ts
simplex.wallet.address
simplex.wallet.balances()
await simplex.wallet.send({ chain: "EVM-8453", token: "0x…", amount: "100", to: "0x…" })
await simplex.wallet.history()

await simplex.pause()      // stop filling; monitoring continues, persisted across restarts
await simplex.resume()
simplex.status()
await simplex.activity()
await simplex.bidStats()   // watch `pendingRetraction`: deposits still locked
```

## Persisting runtime edits

Mutations update the live config object, so `simplex.config()` always reflects what is actually
running. Pass `onConfigChange` to persist it however you like:

```ts
const simplex = await Simplex.start({
    config,
    data: new SqliteDataStore("./simplex-data"),
    onConfigChange: async (config) => {
        await db.settings.put("filler-config", config)
    },
})
```

Without it, edits apply live but do not survive a restart — `configPath` alone does not persist them;
it is informational. The binary supplies a handler that writes the TOML file back.

## Self-halt

Overfill protection halts the engine if consecutive orders clamp against the output ceiling, which
usually means a systemic pricing error. A halted solver refuses every order until an operator
clears it:

```ts
if (simplex.isHalted()) {
    await alert("simplex halted — check pricing")
    simplex.resetHalt()
}
```

## Running more than one

Instances share no state, so several solvers can run in one process — different keys, different
chains, different books:

```ts
const [eu, apac] = await Promise.all([
    Simplex.start({ config: euConfig, data: new SqliteDataStore("./data/eu") }),
    Simplex.start({ config: apacConfig, data: new SqliteDataStore("./data/apac") }),
])
```

Give each its own data directory. Two solvers sharing one bid store would each see the other's bids
as theirs to retract.

Started like that, each solver scans the chains itself. Two solvers watching Base issue two
identical `getLogs` streams forever, because the filter carries nothing solver-specific — so at any
real fleet size the scanning, not the filling, is what exhausts an RPC quota. Share a stream instead.

## Sharing a scanner

Build an `OrderStream` and hand it to the solvers that should share it:

```ts
import { Simplex, OrderStream, HyperbridgeStream } from "@hyperbridge/simplex"

const orders      = await OrderStream.create(config.chains)
const hyperbridge = await HyperbridgeStream.create(config.simplex.hyperbridgeWsUrl)

const eu   = await Simplex.start({ config: euConfig,   orderStream: orders, hyperbridgeStream: hyperbridge })
const apac = await Simplex.start({ config: apacConfig, orderStream: orders, hyperbridgeStream: hyperbridge })

// Yours to close, whenever both solvers are done with it.
await orders.close()
await hyperbridge.close()
```

`OrderStream.create` takes the same array as your config's `chains`, so it can be passed straight
through. Entries without a `chainId` have it read back from their own endpoints, which also proves
they answer for one chain before a solver depends on them.

The Hyperbridge stream matters more than it looks: phantom polling re-reads *every* Hyperbridge
block, and it goes through `offchain_localStorageGet`, which requires `--rpc-methods=unsafe` — so it
can only ever hit your own node. Bid submission is unaffected either way; it is signed with each
solver's own substrate key on its own connection.

<Callout type="info">
    Omit both and a solver builds private streams from its own config and closes them on `stop()`.
    Nothing is ever shared implicitly — sharing is something you do on purpose.
</Callout>

### Who owns what

A stream you pass in is yours. Solvers subscribe and unsubscribe; none of them closes it, and
`stop()` leaves it running for whoever else is reading.

That rule reaches the chain controls. `chains.add`, `chains.remove` and `chains.setRpcUrls` edit a
stream the solver built for itself, and refuse on one you supplied:

> Endpoints for chain 8453 belong to the order stream you supplied — change them there, so the other
> solvers reading it are not repointed underneath them.

Manage a shared stream through the stream: `orders.addChain({ rpcUrls, bundlerUrl })`,
`orders.removeChain(chainId)`, `orders.chains()`.

### What sharing costs you

Delivery is at-least-once, so a stream that resumes from a cursor after a reconnect re-delivers.
Solvers de-duplicate on `order.id`; a custom subscriber must too.

A stream never blocks on a slow subscriber — one would otherwise stall every other solver reading
it. A subscriber that falls behind loses its oldest events instead, and `subscription.dropped`
counts them, so the loss is visible rather than silent.

## Logging

**The library writes nothing anywhere until you tell it where.** Importing
`@hyperbridge/simplex` does not touch your stdout, install a formatter, or spawn a transport worker —
a library has no business logging into a host process uninvited.

Point `logger` at any sink: it receives one NDJSON record per line, and anything Writable-shaped
works.

```ts
import { createWriteStream } from "node:fs"

const simplex = await Simplex.start({
    config,
    logger: createWriteStream("solver.log", { flags: "a" }),
})
```

Forwarding into a logger you already have is the same shape:

```ts
const simplex = await Simplex.start({
    config,
    logger: { write: (line) => myLogger.write(JSON.parse(line)) },
})
```

Or `process.stdout` if you do want it on the console. For the binary's colourised output, pipe
through `pino-pretty` yourself — formatting is a presentation choice that belongs to your
application, not to this package.

Set verbosity with `config.simplex.logging`, or `simplex.setLogLevel("warn")` on a running solver,
which applies immediately including to services already constructed. Level alone produces no output;
a sink is still required.

Logging is scoped to the solver, not the process. Each `Simplex` owns its own destination and level,
so several solvers in one process keep their records apart:

```ts
const [eu, apac] = await Promise.all([
    Simplex.start({ config: euConfig, logger: euLog }),
    Simplex.start({ config: apacConfig, logger: apacLog }),
])

await eu.setLogLevel("debug")     // apac stays at its own level
eu.addLogSink(auditStream)        // and its own sinks
```

`addLogSink(sink)` at module level registers a destination on the process-wide fallback context,
which is what code outside a solver's lifetime uses — the validators, and the `simplex` binary
itself. A running solver never writes there.

## Validating a config without starting

The validators are pure and run the same rules boot does, so you can gate a config — from a form, a
database, an API — before committing to a start:

```ts
import { validateConfig, validatePairConfigs, bookCrossedAt } from "@hyperbridge/simplex"

validateConfig(config)                       // throws with a descriptive message
validatePairConfigs(config.pairs!)

// A crossed book is legal but means a full round trip loses money — worth warning on.
const crossed = bookCrossedAt(pair.bidPriceCurve!, pair.askPriceCurve!)
if (crossed) console.warn(`book crosses at ${crossed.amount}`)
```

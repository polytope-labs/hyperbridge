# Cancelling Orders

An Intent Gateway order can be cancelled to reclaim unfilled escrow. The route depends on whether the order is same-chain or cross-chain, and, for cross-chain orders, whether cancellation starts on the source or destination chain. This guide shows every route, the on-chain rules that control it, the transaction you need to sign, and how to track the refund through the Hyperbridge indexer.

The `IntentGateway.cancelOrder()` SDK method abstracts over all three routes. You pass the finalized order returned by `ORDER_PLACED`, an `IsmpClient` for proof/indexer access, and optionally `{ from: "destination" }`. For same-chain orders, the SDK always uses the direct local path, even if you pass `from: "destination"`.

At each `AWAITING_CANCEL_TRANSACTION` yield, pass either a **serialized signed transaction** (raw bytes) or a **transaction hash** (`0x` + 64 hex chars) back via `gen.next()`. If you pass a hash, the SDK assumes the transaction has already been submitted and will wait for the receipt; if you pass raw bytes, it broadcasts first.

<Callout type="warn">
Keep the **finalized `Order`** from the placement flow, including `id`, fee-reduced `inputs`, `session`, user, source, destination, nonce, and deadline. The gateway hashes the complete order for cancellation; rebuilding it from the original draft can produce a different commitment and revert. The indexer is excellent for tracking an order, but it is not a substitute for persisting the finalized order object.
</Callout>

## Choose the cancellation route

| Order type and route | Who may start it | When it may start | What happens |
| --- | --- | --- | --- |
| Same-chain | Original user through the deadline; anyone strictly after it | Any time before it is fully filled | Source gateway refunds remaining escrow directly in the same transaction. |
| Cross-chain, **from source** | Original order user only | Only after a destination proof height is **strictly greater** than `order.deadline` | Source gateway dispatches an ISMP GET request to prove the destination fill amounts and calculate the unfilled remainder. |
| Cross-chain, **from destination** | Original user through the deadline; anyone strictly after it | Any time before or after expiry | Destination gateway locks the order against fills and dispatches a `RefundEscrow` POST message to the source. |

For same-chain and destination-side cancellation, the contract requires the original user while `_blockNumber() <= order.deadline`. The deadline block itself is still user-only; a third party can cancel from the first block strictly after it. `_blockNumber()` is the L2 block height on Arbitrum, matching `eth_blockNumber`; it is not a timestamp or an L1 block-height field.

A third-party caller pays the cancellation transaction gas and receives no escrow or fee refund. The finalized order remains in calldata, and the gateway always sends the remaining escrow to `order.user`, so the caller cannot redirect it.

### What is refunded and what is not

| Amount | On a successful cancellation |
| --- | --- |
| Remaining input escrow | Refunded to `order.user`. After a partial fill, only the unfilled remainder is refundable, including for cross-chain orders. |
| `order.fees` solver/settlement fee | Refunded to `order.user` when the refund finalizes on the source chain. |
| Protocol fee deducted at placement | The portion attributable to refunded input escrow is returned to `order.user`; the protocol keeps the portion attributable to released escrow. Applies to orders placed after the fee-refund upgrade. |
| Placement gas and cancellation gas | **Not refunded.** They are native-chain transaction costs. |

For each input token, the gateway records the exact protocol fee charged at placement and the original input amount committed after deducting that fee. On cancellation it returns:

```text
fee refund = floor(placement fee × refunded input escrow / original committed input)
```

The same rule applies to voluntary cancellation before expiry and cancellation after expiry. For example, a 1,000-token input with a 1% fee commits 990 tokens and holds a 10-token fee. If 495 escrowed tokens are released before the rest is cancelled, the user receives 495 escrowed tokens plus 5 fee tokens. The other 5 fee tokens become protocol revenue. An entirely unfilled order receives its whole fee back.

The formula uses refundable input amounts, including existing partial-fill rounding, rather than the percentage of output filled. Fee refunds round down in the token's smallest unit; the remainder becomes protocol revenue. Later changes to the configured fee rate do not change the recorded fee. For tokens that charge a transfer fee, placement accounting uses the amount actually received by the gateway, and a tax on the outgoing refund can reduce what the user receives.

Cross-chain refunds exclude principal already earned by solvers, even if their redemption messages have not yet reached the source. Orders placed **before the fee-refund upgrade** retain their original treatment: their protocol fees were already collected as dust and are not refundable.

## Contract rules at a glance

All routes enter `IntentGatewayV2.cancelOrder`. The gateway derives the order commitment, rejects an already-settled commitment, and routes same-chain work to `IntrinsicModule.cancelSameChain`; the two cross-chain routes delegate to `ExtrinsicModule`. The route-specific authorization predicates are:

```solidity
// Same-chain route: user through the deadline; public only after it.
if (order.user != bytes32(uint256(uint160(msg.sender))) && _blockNumber() <= order.deadline) {
    revert Unauthorized();
}

// Source route: user only, and proof height must be after the deadline.
if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
if (options.height <= order.deadline) revert NotExpired();

// Destination route: user through the deadline; public only after it.
if (order.deadline >= _blockNumber()) {
    if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
}
```

This explains the trade-off:

- Choose the **destination route** when the user wants to recover promptly, including before expiry. It definitively prevents a future fill before the refund travels back to the source.
- Choose the **source route** only after expiry when the user controls the source wallet and prefers proving the destination fill amounts to recover the unfilled remainder.
- Choose the **same-chain route** for a direct refund with no messaging fee. The user can submit it through the deadline, and a keeper can submit it strictly after expiry.

### `CancelOptions`

```solidity
struct CancelOptions {
    uint256 relayerFee;  // Fee paid to the Hyperbridge relayer (cross-chain cancels only)
    uint64 height;       // Proof height for source-side cancels; must be > order.deadline
}
```

`height` is only meaningful for source-side cross-chain cancels. It must point to a block after the order deadline, ensuring the proof captures fill amounts after further fills are no longer allowed. The SDK selects this value automatically. For same-chain and destination-side cancels, `height` is ignored.

### The `OrderCancelled` event

```solidity
// Emitted on whichever chain the cancellation was initiated from.
event OrderCancelled(bytes32 indexed commitment, address canceller);
```

`cancelOrder` emits this once, before it routes to any of the three cancellation paths, so it fires the moment a cancellation is initiated whichever route handles it. Every route-specific check reverts, and a revert discards logs, so the event never announces a cancellation that did not happen. It is the only signal keyed to the order that a cross-chain cancel produces on the initiating chain; the host's `GetRequestEvent` and `PostRequestEvent` carry no reference to the order.

`canceller` is `msg.sender`. On same-chain and destination routes that need not be `order.user`: after the deadline anyone may cancel, so this is the record of who submitted the transaction.

### The `EscrowRefunded` event

```solidity
// Emitted on the source chain when escrowed tokens are returned to the user.
event EscrowRefunded(bytes32 indexed commitment, TokenInfo[] tokens);
```

`EscrowRefunded` remains the terminal event — `OrderCancelled` says a cancellation started, this one says the money is back. For same-chain cancels it follows in the same transaction. For source-side cross-chain cancels, it is emitted once Hyperbridge delivers the destination proof back to the source chain and the refund is processed. For destination-side cancels, it is emitted on the source chain once the refund message from Hyperbridge is received and settled.

### The `ProtocolFeeRefunded` event

```solidity
event ProtocolFeeRefunded(bytes32 indexed commitment, address indexed token, uint256 amount);
```

The source gateway emits this event for each nonzero protocol-fee refund. `EscrowRefunded.tokens` continues to contain only the input escrow; add `ProtocolFeeRefunded.amount` for the corresponding token to obtain the total input-token refund. Both events report amounts transferred by the gateway, before any outgoing token transfer tax.

Protocol fees are held until the order settles. `DustCollected` reports only the earned fee at settlement, not the held fee at placement. Other sources of dust, such as surplus, still emit `DustCollected` when collected.

```typescript lineNumbers title="setup.ts" icon="typescript"
const sourceChain = await EvmChain.create(SOURCE_RPC_URL)

```

## Preflight: use the finalized order and check on-chain state

Run these checks immediately before starting any route. `isOrderFilled()` means the commitment is settled, but it cannot distinguish a completed fill from a destination-side cancellation because both set the same settled marker. `isOrderRefunded()` is the definitive confirmation that escrow made it back to the user.

```typescript title="preflight-cancel.ts" lineNumbers
async function assertCancellable(order: Order) {
  if (await intentGateway.isOrderRefunded(order)) {
    throw new Error("Order was already refunded")
  }

  if (await intentGateway.isOrderFilled(order)) {
    throw new Error("Order is already filled or destination-cancelled")
  }
}

await assertCancellable(finalizedOrder)
```

For a destination-side cancel before expiry, ensure the signer is the same address as `finalizedOrder.user`. After expiry, a keeper or relayer may pay for the destination cancellation, but the `RefundEscrow` message still names `order.user` as beneficiary. An outside caller cannot redirect the refund.

## Same-Chain Orders

For same-chain orders, the gateway returns escrow directly on the order's chain. The order user can cancel through the deadline. Strictly after the deadline, a keeper can submit the same calldata from its own wallet; the keeper pays native gas, while all remaining escrow and refundable `order.fees` still go to `order.user`. No Hyperbridge message or relayer fee is involved.

If the order has been partially filled, the escrowed balance will already be reduced proportionally. The refund covers only what remains.

The keeper must use SDK chain clients and a wallet for the finalized order's source/destination chain. The Ethereum setup above can create a same-chain gateway by passing `sourceChain` on both sides:

```typescript lineNumbers title="cancel-expired-same-chain.ts" icon="typescript"
async function cancelExpiredSameChain(order: Order) {
  const orderSource = normalizeStateMachineId(order.source)
  const orderDestination = normalizeStateMachineId(order.destination)
  if (
    orderSource !== orderDestination ||
    orderSource !== sourceChain.config.stateMachineId ||
    keeperWallet.chain.id !== mainnet.id
  ) {
    throw new Error("Gateway and keeper wallet must target the order's same chain")
  }
  const sameChainGateway = await IntentGateway.create(sourceChain, sourceChain, coprocessor)
  const sameChainIndexer = new IsmpClient({
    queryClient,
    source: sourceChain,
    dest: sourceChain,
    hyperbridge,
  })
  const currentBlock = await sourceChain.client.getBlockNumber({ cacheTime: 0 })
  if (currentBlock <= order.deadline) throw new Error("Order has not expired")
  if (await sameChainGateway.isOrderFilled(order)) {
    throw new Error("Order already settled")
  }

  const cancellation = sameChainGateway.cancelOrder(order, sameChainIndexer)
  try {
    const pending = await cancellation.next()
    if (pending.done || pending.value.status !== "AWAITING_CANCEL_TRANSACTION") {
      throw new Error("Expected a same-chain cancellation transaction")
    }
    const { to, data, value } = pending.value
    const hash = await keeperWallet.sendTransaction({
      account: keeperWallet.account,
      chain: keeperWallet.chain,
      to,
      data,
      value,
      type: "eip1559",
    })
    const result = await cancellation.next(hash)
    if (result.done || result.value.status !== "CANCELLATION_COMPLETE") {
      throw new Error("Cancellation did not complete")
    }
    if (!(await sameChainGateway.isOrderRefunded(order))) {
      throw new Error("Refund is not confirmed on-chain")
    }
    console.log("Refunded to the order user:", result.value.transactionHash)
  } finally {
    await cancellation.return(undefined)
  }
}

await cancelExpiredSameChain(finalizedOrder)
```

Preflight checks reduce failed transactions but do not reserve the order; the contract remains authoritative if a fill or another cancellation lands first. A concurrent cancellation can make this transaction revert with `Filled`. Re-check `isOrderRefunded(order)` before reporting a refund, rather than treating that error by itself as proof. The keeper wallet also needs enough native currency for transaction gas.

## Cross-Chain Orders

Cross-chain cancellations require Hyperbridge to either prove the destination fill amounts (source-side cancel) or deliver a refund message (dest-side cancel). Both paths involve a Hyperbridge dispatch fee. Quote it with `quoteCancelOrder` before signing. The SDK handles proof fetching, finality monitoring, and Hyperbridge submission automatically.

### Cancel from the Source Chain

Cancelling from the source chain proves how much of the order was filled on the destination. The contract queries the destination's `_partialFills` storage at a block height after the deadline and refunds the proven unfilled principal plus its protocol-fee share. Principal already earned by solvers remains available for their redemption messages. A proof that the order was fully filled returns no principal or protocol fee; pending fees are settled by the final solver redemption.

Because the proof must come from a block after the order deadline, this path is only available once the order has expired. The SDK automatically selects the appropriate block height.

You only need to sign and submit the `cancelOrder` transaction on the source chain. The SDK fetches the destination storage proof, monitors finality on both sides, and submits everything to Hyperbridge automatically.

```typescript lineNumbers title="cancel-from-source.ts" icon="typescript"
async function cancelFromSource(order: Order) {
  if (await intentGateway.isOrderFilled(order)) {
    throw new Error("Order already filled")
  }

  const gen = intentGateway.cancelOrder(order, indexerClient)
  for await (const event of gen) {
    switch (event.status) {
      case "DESTINATION_FINALIZED":
        // SDK fetched a storage proof from the destination at a height > order.deadline
        console.log("Destination proof at height:", event.proof.height)
        break

      case "AWAITING_CANCEL_TRANSACTION": {
        // SDK encodes cancelOrder calldata (with the proof height embedded) and yields it here.
        // value is the quoted native fee for the GET request dispatch; include it in the tx.
        const { data, to, value } = event

        const signedTx = await sourceWallet.signTransaction({
          to,
          data,
          value,
          type: "eip1559",
        })

        // Pass the signed tx back. The generator broadcasts the tx, then yields CANCEL_STARTED.
        // gen.next() here consumes CANCEL_STARTED so the for-await resumes at SOURCE_FINALIZED.
        const { value: cancelStarted } = await gen.next(signedTx)
        if (cancelStarted?.status === "CANCEL_STARTED") {
          console.log("Cancel tx confirmed:", cancelStarted.receipt.transactionHash)
        }
        break
      }

      case "SOURCE_FINALIZED":
        // The GET request has been finalised on the source chain.
        // The SDK fetches a source proof, waits for the challenge period, and
        // submits the GET request to Hyperbridge automatically; no action needed.
        console.log("GET request finalised on source:", event.metadata.transactionHash)
        break

      case "HYPERBRIDGE_DELIVERED":
        console.log("GET request delivered to Hyperbridge:", event.metadata.transactionHash)
        break

      case "HYPERBRIDGE_FINALIZED":
      // metadata.calldata is the encoded handleGetResponses call to submit to the
      // ISMP handler on the source chain. This triggers onGetResponse, which
      // verifies the _partialFills amounts and refunds the unfilled principal
      // plus its protocol-fee share.
      const { calldata: handleCalldata } = event.metadata
      // Fetch the handler address from the source ISMP host
      const { handler: handlerAddress } = await sourceChain.client.readContract({
        address: sourceChain.config.host,
        abi: EvmHostABI,
        functionName: "hostParams",
      })
      const receipt = await sourceWallet.sendTransaction({
        to: handlerAddress,
        data: handleCalldata,
      })
      // Confirm the escrow was actually refunded
      const [refundLog] = parseEventLogs({
        abi: IntentGatewayV2ABI,
        eventName: "EscrowRefunded",
        logs: receipt.logs,
      })
      if (!refundLog) throw new Error("EscrowRefunded log not found; refund may have failed")
      console.log("Escrow refunded at block:", receipt.blockNumber)
      return
    }
  }
}
```

The SDK polls the destination chain until it can read the fill amounts at a height past the order deadline, then encodes the `cancelOrder` calldata and yields `AWAITING_CANCEL_TRANSACTION`. You sign the transaction and pass it back. The generator broadcasts it and yields `CANCEL_STARTED`. From there, the SDK handles proof fetching, waiting for the challenge period, and submitting to Hyperbridge. No further action is needed. After finalization, a relayer delivers the response to the source chain, which verifies the destination's `_partialFills` amounts and refunds the unfilled principal plus its protocol-fee share. A fully filled proof refunds zero; the final redemption settles the pending fees.

### Cancel from the Destination Chain

Cancelling from the destination chain is simpler and does not require a storage proof. The destination gateway immediately marks the order as settled, blocking any future fill attempts, and sends a refund message to the source chain via Hyperbridge. When the message arrives, the source chain authenticates it as coming from the registered destination gateway and returns the proven unfilled escrow and its refundable protocol fee to the original user.

Before and **at** the order deadline only the order creator can trigger this path. From the first destination block after the deadline, anyone may call. This lets relayers act on behalf of users whose orders have expired without being filled, providing a recovery mechanism that does not require the user to be online. The caller pays the dispatch cost, but cannot change `WithdrawalRequest.beneficiary`: the refund always goes to `order.user`.

<Callout type="info">
The native `value` in the `AWAITING_CANCEL_TRANSACTION` event already includes the quoted Hyperbridge dispatch fee. Pass it directly to the transaction without a separate quote call.
</Callout>

```typescript lineNumbers title="cancel-from-dest.ts" icon="typescript"
async function cancelFromDest(order: Order) {
  if (await intentGateway.isOrderFilled(order)) {
    throw new Error("Order already filled or cancelled from dest")
  }

  const gen = intentGateway.cancelOrder(order, indexerClient, { from: "destination" })

  // First yield: AWAITING_CANCEL_TRANSACTION, including the quoted native fee for the dispatch
  const { value: { data, to, value } } = await gen.next()

  const signedTx = await destWallet.signTransaction({
    to,
    data,
    value,
    type: "eip1559",
  })

  // Pass signed tx back. SDK confirms the tx and yields CANCEL_STARTED.
  const { value: cancelStarted } = await gen.next(signedTx)
  if (cancelStarted?.status === "CANCEL_STARTED") {
    console.log("cancelOrder tx confirmed:", cancelStarted.receipt.transactionHash)
  }

  // Continue with the remaining status stream
  for await (const event of gen) {
    switch (event.status) {
      case "SOURCE_FINALIZED":
        // The refund message has been finalised on the destination chain.
        console.log("Refund message finalised:", event.metadata.transactionHash)
        break

      case "HYPERBRIDGE_DELIVERED":
        console.log("Refund message delivered to Hyperbridge:", event.metadata.transactionHash)
        break

      case "HYPERBRIDGE_FINALIZED":
        console.log("Refund message finalised on Hyperbridge:", event.metadata.transactionHash)
        break

      case "CANCELLATION_COMPLETE":
        console.log("Escrowed tokens refunded:", event.transactionHash)
        return
    }
  }
}
```

The SDK encodes the `cancelOrder` calldata for the destination gateway and yields `AWAITING_CANCEL_TRANSACTION`. You sign the transaction with sufficient `value` to cover the Hyperbridge dispatch fee and pass it back. Once confirmed, the generator yields `CANCEL_STARTED`. The gateway marks the order as settled and sends a refund message via Hyperbridge. A relayer delivers the message to the source chain, which authenticates the sender and issues the refund.

## Quoting and paying the cancellation fee

Same-chain cancellation has no Hyperbridge dispatch, so both values are `0n`. Cross-chain cancellation has a relayer fee with two payment rails:

| Payment rail | What to send | When to use it |
| --- | --- | --- |
| Native token (recommended) | The `value` yielded by `AWAITING_CANCEL_TRANSACTION` | Standard wallet flow; the gateway buys the fee token through its configured router. |
| Fee token | Approve exactly `relayerFee` to the gateway, then submit the cancellation transaction with `value: 0n` | A wallet or smart account already holding the fee token, or an integration batching exact approvals. |

The generator automatically quotes the native route and exposes it as `value`. Use `quoteCancelOrder()` before starting when you want to display either amount to the user, prepare a fee-token approval, or decide whether a sponsored cancellation is economical.

```typescript lineNumbers title="quote-cancel.ts" icon="typescript"
// GET request fee for source-side cancellation (available only after expiry).
const sourceQuote = await intentGateway.quoteCancelOrder(order)
console.log("Source native value (wei):", sourceQuote.nativeValue)
console.log("Source relayer fee token amount:", sourceQuote.relayerFee)

// POST request fee for destination-side cancellation.
const destQuote = await intentGateway.quoteCancelOrder(order, { from: "destination" })
console.log("Destination native value (wei):", destQuote.nativeValue)
console.log("Destination relayer fee token amount:", destQuote.relayerFee)
```

To use the fee-token rail, approve the fee on the chain that initiates the cancellation. Use the source chain for the source route and the destination chain for the destination route. Then sign the yielded transaction with `value: 0n`:

```typescript title="cancel-with-fee-token.ts" lineNumbers
import { parseAbi } from "viem"

async function cancelWithFeeToken(order: Order, from: "source" | "destination") {
  const payerChain = from === "source" ? sourceChain : destChain
  const payerWallet = from === "source" ? sourceWallet : destWallet
  // Source is the SDK default; only destination needs an explicit option.
  const cancelOptions = from === "destination" ? { from: "destination" as const } : {}
  const quote = await intentGateway.quoteCancelOrder(order, cancelOptions)
  const { address: feeToken } = await payerChain.getFeeTokenWithDecimals()
  const gatewayAddress = payerChain.configService.getIntentGatewayAddress(
    payerChain.config.stateMachineId,
  )
  const erc20Abi = parseAbi([
    "function approve(address spender, uint256 amount) returns (bool)",
  ])

  // Per-cancellation approval: no unlimited allowance is necessary.
  const approvalHash = await payerWallet.writeContract({
    address: feeToken,
    abi: erc20Abi,
    functionName: "approve",
    args: [gatewayAddress, quote.relayerFee],
  })
  await payerChain.client.waitForTransactionReceipt({ hash: approvalHash })

  const cancel = intentGateway.cancelOrder(order, indexerClient, cancelOptions)
  const first = await cancel.next()
  if (first.done || first.value.status !== "AWAITING_CANCEL_TRANSACTION") {
    throw new Error("Expected cancellation transaction")
  }

  const signed = await payerWallet.signTransaction({
    to: first.value.to,
    data: first.value.data,
    value: 0n, // dispatchWithFeeToken() spends the exact approved relayerFee
    type: "eip1559",
  })
  return cancel.next(signed)
}
```

The dispatch fee for starting a cross-chain cancellation is not recovered from the cancelled order. The source-chain refund returns the unfilled input escrow, its refundable protocol fee, and the original `order.fees` when cancellation finalizes; the cancellation caller separately pays the new `relayerFee` above.

## Track cancellation with the indexer and on-chain checks

The cancellation generator is the best live tracker for the ISMP transport. It emits `DESTINATION_FINALIZED`, `CANCEL_STARTED`, `SOURCE_FINALIZED`, `HYPERBRIDGE_DELIVERED`, and `HYPERBRIDGE_FINALIZED` as a cross-chain request progresses. Destination-side cancellation additionally ends with `CANCELLATION_COMPLETE` after the source-chain delivery receipt contains `EscrowRefunded`.

Track the order itself through the attached indexer. The terminal status you want is `REFUNDED`: it means the source chain has processed `EscrowRefunded`, so the remaining escrow and `order.fees` have been returned to `order.user`.

The indexer schema exposes fee refunds through `IOrderV3.protocolFeeRefunds`, separately from `escrowRefunds`. Each record includes `token`, `amount`, `chain`, and `transactionHash`. Fee records do not change the order's status. The SDK's `queryOrder()` and status stream continue to track settlement; use the fee-refund events or indexer relation when displaying a refund breakdown.

```typescript title="track-order-refund.ts" lineNumbers
import { OrderStatus } from "@hyperbridge/sdk"

// The order ID is the commitment from the ORDER_PLACED update.
const current = await intentGateway.queryOrder(finalizedOrder.id!)
console.log("Latest indexed status:", current?.status)
console.log("History:", current?.statuses)

for await (const update of intentGateway.orderStatusStream(finalizedOrder.id!)) {
  console.log(update.status, update.metadata.transactionHash)

  if (update.status === OrderStatus.REFUNDED) {
    console.log("Refund finalized on the source chain")
    break
  }

  if (update.status === OrderStatus.FILLED || update.status === OrderStatus.REDEEMED) {
    throw new Error("The order was filled and escrow was released to the solver")
  }
}
```

Use on-chain checks as the final truth when the indexer has not indexed the latest block yet:

```typescript lineNumbers title="check-status.ts" icon="typescript"
// Returns true if the order has been settled (filled or dest-cancelled).
const filled = await intentGateway.isOrderFilled(order)

// Returns true if the order was cancelled and escrow was returned (EscrowRefunded event exists).
const refunded = await intentGateway.isOrderRefunded(order)
```

`isOrderFilled` and `isOrderRefunded` can both be true simultaneously. A destination-cancelled order is marked as settled (so `isOrderFilled` returns `true`) and also triggers a refund (so `isOrderRefunded` returns `true` once the source chain processes the refund message). Use `isOrderRefunded` when you specifically need to confirm the user received their tokens back.

<Callout type="info">
For a source-initiated cancellation, `HYPERBRIDGE_FINALIZED` means the proof round has completed. Continue tracking the order until its indexer status is `REFUNDED` or `isOrderRefunded(order)` is true; that is the user-visible completion point.
</Callout>

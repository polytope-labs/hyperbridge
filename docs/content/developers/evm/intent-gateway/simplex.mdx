# Simplex

Simplex is an automated binary that monitors Intent Gateway orders and fills them profitably. It watches configured chains for `OrderPlaced` events, waits for sufficient confirmations based on the order's value, prices each order against the configured trading pairs, and fills when profitable. Solvers earn the difference between order inputs and outputs.

## Quick Start

### Docker (Recommended)

The image is a multi-arch manifest covering `linux/amd64` and `linux/arm64`, so Linux, macOS (Intel and Apple Silicon) and Windows (Docker Desktop / WSL2) hosts all pull a natively-built image — no emulation, no per-host build.

```bash lineNumbers
docker pull polytopelabs/simplex:latest
docker run --rm -it polytopelabs/simplex:latest --help
```

Starting with no config puts the container into the setup wizard. Publish the UI port and give it a volume to write the generated config into:

```bash lineNumbers
docker volume create simplex-data
docker run -d --name simplex --restart unless-stopped \
    -p 127.0.0.1:8686:8686 \
    -p 127.0.0.1:9090:9090 \
    -v simplex-data:/data \
    polytopelabs/simplex:latest
```

Then open `http://localhost:8686`. The wizard writes `filler-config.toml` into `/data` and transitions straight into running the solver; on restart the container finds that config and runs directly. Mount a config you already have with `-v /path/to/filler-config.toml:/data/filler-config.toml:ro` to skip the wizard, or run it in the terminal instead with `docker run --rm -it -v simplex-data:/data polytopelabs/simplex:latest init -o /data/filler-config.toml`.

The command works verbatim in PowerShell on Windows (use a backtick instead of `\` for line continuations, or put it on one line). Ports have to be published — the container binds `0.0.0.0` internally because Docker Desktop on macOS and Windows runs the daemon inside a VM and offers no `--network host`. The container's network namespace is the boundary there, so keep the `127.0.0.1:` prefix on the published ports: the UI is unauthenticated, and the wizard handles private keys.

## Markets

Simplex is a single pair engine. Every market it serves — cross-asset swaps like USDC/cNGN and same-asset cross-chain transfers like USDC→USDC — is a **`[[pairs]]`** entry in your TOML config, priced by its own bid/ask curves. Pairs reference assets by symbol from the built-in [asset registry](#the-asset-registry), and an LP can declare any number of them. Both **same-chain** and **cross-chain** orders are supported.

Same-chain orders (`source == destination`) are filled immediately without waiting for additional confirmations. Cross-chain orders wait per the configured [confirmation policy](#confirmation-policy) before bidding.

An order is filled only when **two independent checks both pass**:

1. **Fees cover execution.** `order.fees` must cover the fill gas and, for a cross-chain order, the **relayer fee** for delivering the escrow-release message back to the source chain (a ~1M-gas cost priced on the source chain; zero for same-chain fills). The swap spread is never credited toward this — fees must stand on their own.
2. **Every same-token leg nets a positive spread.** A same-asset cross-chain transfer must leave the solver holding more of the asset than it sent, measured in that asset's own units. Legs are never summed across pairs — margins in different quote assets share no unit, and a winning leg in one currency must not mask a losing leg in another.

Cross-asset and one-sided legs are deliberately **not** gated on margin: they fill at the operator's own curve, which is the price the operator declared acceptable. Their margin is computed and logged, but never used to reject an order. A crossed book (bid at or below ask) is allowed for the same reason — each side is quoted and filled independently at its own curve, so crossing only means a full round trip loses money. The wizards surface it as a warning, not a startup error. Skew both curves to manage inventory, or use a one-sided pair for a deliberate directional position.

The solver holds inventory on both sides of its pairs. When a user swaps token0→token1 the solver sells token1 at the pair's ask price; when the user swaps token1→token0 the solver buys at the bid price. The spread between the two curves is the solver's margin per trade.

Curves are expressed in **token1 per 1 token0** and keyed by the order's token0 notional. A higher bid means the solver owes less token0 per token1 received (it profits more buying token1). A lower ask means the solver sends fewer token1 per token0 received (it profits more selling token1).

Each pair's **`maxOrderSize`** caps the solver's exposure per order, denominated in that pair's token0. An order whose requested output exceeds what the cap allows is **skipped entirely**, not partially filled. The skip is logged with `limiter: "maxOrderSize"`, which distinguishes it from an order the solver declined because its own curve yields less than the user asked for (`limiter: "price"`) — the two have different operator fixes.

Simplex always uses the solver selection path: it submits a signed bid to Hyperbridge via `IntentsCoprocessor` rather than calling `fillOrder` directly. This requires `substratePrivateKey` and `hyperbridgeWsUrl` in `[simplex]`, plus a `bundlerUrl` on each `[[chains]]` entry.

On startup, Simplex automatically delegates the solver's EOA to the `SolverAccount` contract via EIP-7702 — submitting a no-op UserOp through the bundler so the delegation lands without requiring the EOA to hold native gas. A paymaster covers the delegation tx (and subsequent fills) in stablecoins on chains where one is deployed: the Circle Paymaster (USDC) is tried first, then the `SimplexPaymaster` (USDC or USDT), which is live on Ethereum, Arbitrum, Base, Polygon, and BSC — see [Mainnet Contract Addresses](/developers/evm/contract-addresses/mainnet). On chains without any paymaster, Simplex falls back to a direct type-0x04 delegation tx and tops up the ERC-4337 EntryPoint deposit to cover `targetGasUnits` (default 3M) at current gas price.

```toml lineNumbers
# Trading pairs — assets are referenced by symbol from Simplex's built-in
# registry; declare as many pairs as you like, one FX engine serves them all.
[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # per-order cap, in token0 units (5000 USDC)
# Bid: CNGN per USDC when *buying* CNGN from a user (CNGN→USDC leg).
bidPriceCurve = [
    { amount = "100",  price = "1580" },
    { amount = "1000", price = "1575" },
    { amount = "5000", price = "1570" },
]
# Ask: CNGN per USDC when *selling* CNGN to a user (USDC→CNGN leg).
askPriceCurve = [
    { amount = "100",  price = "1560" },
    { amount = "1000", price = "1555" },
    { amount = "5000", price = "1550" },
]

[[pairs]]
token0 = "USDT"
token1 = "CNGN"
maxOrderSize = "5000"
bidPriceCurve = [ { amount = "0", price = "1578" } ]
askPriceCurve = [ { amount = "0", price = "1552" } ]

# A rand/naira book — no USD asset involved; sized entirely in ZARP:
[[pairs]]
token0 = "ZARP"
token1 = "CNGN"
maxOrderSize = "90000"      # 90,000 ZARP per order
bidPriceCurve = [ { amount = "0", price = "86" } ]   # CNGN per ZARP
askPriceCurve = [ { amount = "0", price = "84" } ]

# A same-asset cross-chain market (USDC→USDC):
# the ask price below par IS the spread.
[[pairs]]
token0 = "USDC"
token1 = "USDC"
maxOrderSize = "100000"
askPriceCurve = [
    { amount = "100",    price = "0.99"  },   # small orders: 1% spread
    { amount = "100000", price = "0.999" },   # large orders: 0.1%
]
```

#### The asset registry

Pairs reference assets purely by symbol — no address configuration. Every shipped symbol resolves per chain from the **SDK chain registry** (`chain.ts`), the single source of truth for token addresses shared with the rest of the SDK: **USDC, USDT, DAI, cNGN** (testnets included) plus curated stablecoin deployments on the supported mainnets — **USDR** (DollarCoin US dollar — Ethereum, Base, Polygon), **ZARP** (South African rand — Ethereum, Polygon, Base), **EURC** (Circle euro — Ethereum, Base), **XSGD** (StraitsX Singapore dollar — Ethereum, Polygon) and **TRYB** (BiLira Turkish lira — Ethereum). Curated addresses are taken from the issuer's official documentation and verified on-chain (`symbol()`/`decimals()`) before inclusion, and a new asset is added once in the SDK registry — there is no parallel table in Simplex to drift out of sync. Symbols are case-insensitive; a pair simply doesn't trade on chains where an asset isn't deployed.

The registry holds addresses only — it carries no prices. Every quantity that sizes a pair is denominated in the pair's own `token0`: the curve `amount` axis and the per-order `maxOrderSize` cap. The curves are the only price source — including for confirmation sizing, where the order's USD value is derived from them (see below).

For assets the registry doesn't ship — or to override an address for your deployment — the optional **`[assets]`** table is the escape hatch, a bare symbol → chain → address map:

```toml lineNumbers
# Only needed for assets the registry does not ship (or overrides):
[assets.BRZ]
"EVM-137" = "0xBrzOnPolygon"

[[pairs]]
token0 = "USDC"
token1 = "BRZ"
maxOrderSize = "5000"
askPriceCurve = [ { amount = "0", price = "5.4" } ]
```

#### Trading pairs

Each **`[[pairs]]`** entry is one market: `token0`/`token1` symbols, a per-order **`maxOrderSize`** cap in token0 units, and bid/ask curves in **token1 per token0** keyed by token0 notional. Every pair is priced, capped, and sized independently — USDC/cNGN and USDT/cNGN can carry different rates, so a USDT depeg is handled by adjusting one pair's curves (live, from the local web dashboard the `run` command serves on `--ui`) instead of being silently absorbed. Orders whose legs match no configured pair are rejected, so the pair list doubles as an allowlist of the markets the LP serves.

Cross-chain confirmation policies are sized with the order's **USD value**, derived entirely from your own curves: USDC/USDT/DAI are $1 anchors, and every curve-priced cross-asset pair is an FX edge between its two symbols. That makes an anchor a startup requirement — every pair's `token0` must be a USD stable or connect to one through your curve-priced pairs, directly or transitively (USDC/cNGN plus ZARP/cNGN anchors ZARP through cNGN). A config with an unanchorable `token0` refuses to start. An anchoring pair can be declared `referenceOnly = true` to contribute its rate without opening a tradeable market.

#### Same-token markets

A pair may quote the **same symbol on both sides** — the same-asset cross-chain market (USDC on one chain in, USDC on another out). Same-token pairs are **ask-only** (both directions are one market) and their ask prices sit **strictly below par**: the price is the fraction of the input paid back out, so `0.9995` keeps 5 bps of every fill. Prices at or above 1 are rejected at startup — par is a zero spread that can never fill, and above par pays out more than received.

Same-token markets are **cross-chain only** — a same-chain order (source == destination) would be a pay-more-get-less self-swap and is rejected. Any registry asset works, USD-stable or not (e.g. a cNGN/cNGN transfer market across chains): the profit gate checks that each same-token leg comes out ahead **in its own asset** (a unit-independent sign check on input − output), and `order.fees` separately covers execution in the source fee token. The USD-anchor startup rule still applies, and a same-token pair contributes no FX edge of its own — a non-USD same-token market therefore needs a curve-priced USD pair for the asset alongside it (e.g. USDC/cNGN next to cNGN/cNGN) so confirmation depth can be sized in USD. Declare that anchoring pair **`referenceOnly = true`** to supply the rate without opening a market: a reference pair feeds the anchor graph but never matches orders, and needs no `maxOrderSize`.

Unlike cross-asset fills, the same-token spread is **realized in-kind on the fill itself**. It is not credited toward the fee gate, though: `order.fees` must cover execution on their own, and an order whose fees fall short is skipped no matter how wide the spread is. The realized spread only ranks orders that already passed both gates. Pre-position the asset on each destination chain (optionally backed by the [`[vault]` treasury](#vault-treasury-erc-4626)).

#### One-sided LP

With both curves set a pair fills in both directions. Omitting one curve restricts that pair to a single direction, so the solver keeps accumulating one asset while only giving away the other — and each pair is gated independently:

- **Ask only** (omit `bidPriceCurve`) — the solver only *sells* token1 on that pair, filling orders where the user sends token0 and receives token1. It accumulates token0 and gives away token1 (for example, take USDC, hand out cNGN).
- **Bid only** (omit `askPriceCurve`) — the solver only *buys* token1 on that pair, filling orders where the user sends token1 and receives token0.

Orders in the disabled direction are rejected before bidding (an order with mixed-direction legs is rejected as a whole, since the IntentGateway settles all legs atomically).

```toml lineNumbers
# Ask curve only — keep accumulating USDC by only selling cNGN
[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"
askPriceCurve = [
    { amount = "100",  price = "1560" },
    { amount = "1000", price = "1555" },
    { amount = "5000", price = "1550" },
]
```

When pricing from a [Uniswap V4 pool](#pool-based-pricing) (no curves), there is no curve to omit, so set **`side`** on the `[vault.uniswapV4]` block instead — `"ask"` to only sell token1 (accumulate the quote asset) or `"bid"` to only buy token1. Omit `side` to fill both directions. `side` cannot be combined with static curves.

```toml lineNumbers
[assets.CNGN]
"EVM-8453" = "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F"

[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # pool-priced: no curves

[vault.uniswapV4]
side = "ask"  # only sell CNGN; keep accumulating USDC
positions = [
    { chain = "EVM-8453", tokenId = "2087350" },
]
```


#### Uniswap V4 LP funding

<Callout type="info">
This is the **Uniswap V4 LP** funding source, configured under `[vault.uniswapV4]`. It funds (and prices) the **exotic** token from concentrated-liquidity positions. It is distinct from the [`[vault]` stablecoin treasury](#vault-treasury-erc-4626) (ERC-4626), which sources **stablecoins** — the two share the `[vault]` section.
</Callout>

When the solver's wallet balance on the destination chain is insufficient to fill an order, Simplex can automatically withdraw liquidity from on-chain positions to cover the deficit. Withdrawal calls are prepended to the UserOperation as ERC-7821 batch calls, making the funding atomic with the fill.

Configured under the top-level `[vault.uniswapV4]` block. Decreases liquidity from concentrated Uniswap V4 positions via PositionManager NFTs. Slippage tolerance is set by `spreadBps` (default 50 bps / 0.50%), deadline defaults to the order's deadline. Each position needs a `chain` and a `tokenId` (the ERC-721 position NFT ID); pool details are read on-chain at startup.

```toml lineNumbers
[vault.uniswapV4]
positions = [
    { chain = "EVM-8453", tokenId = "123456789" },
]
```

<Callout type="info">
Vaults are initialized at startup; on-demand **refresh** runs before each withdrawal plan so calculations use current on-chain reserves. Simplex can aggregate withdrawals across multiple vaults if needed.
</Callout>

To find your `tokenId`, open your position on the Uniswap V4 app — the token ID is the number in the URL (e.g. `app.uniswap.org/positions/v4/8453/2087350` → `tokenId = "2087350"`).

#### Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

```toml lineNumbers
[assets.CNGN]
"EVM-8453" = "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F"

[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # no curves — priced from the pool

[vault.uniswapV4]
spreadBps = 50  # 0.5% slippage tolerance on LP redemptions
positions = [
    { chain = "EVM-8453", tokenId = "2087350" },
]
```

<Callout type="info">
Startup validation requires a pricing source per pair: **either** bid/ask price curves, **or** at least one `[vault.uniswapV4]` position. A pair with neither fails validation.
</Callout>

#### Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```

#### Example profit calculation

For a \$1000 USDC → cNGN order, the curve interpolates to bid 1575, ask 1555 at the $1000 size:

```
User sends:       $1000 USDC
Solver delivers:  1,555,000 cNGN      (1000 × ask 1555)
Solver's cost:    1,555,000 / 1575    = $987.30  (valued at bid)
Spread profit:    $1000 − $987.30     = $12.70
Fee profit:       $2.80 − $1.30 costs = $1.50
Total profit:     ~$14.20
```

### Signer Configuration

The `[simplex.signer]` section defines how Simplex signs EVM transactions. Two modes are supported:

The signer is a tagged union — set `type` to select the variant, then add the variant's fields directly under `[simplex.signer]`:

**Private Key** — Signs transactions locally using a raw private key:

```toml lineNumbers
[simplex.signer]
type = "privateKey"
key  = "0x..."
```

**MPC Vault** — Signs transactions via [MPC Vault](https://mpcvault.com), an institutional custody service that uses MPC for signing ceremonies:

```toml lineNumbers
[simplex.signer]
type                          = "mpcVault"
apiToken                      = "your-api-token"
vaultUuid                     = "your-vault-uuid"
accountAddress                = "0xYourWalletAddress"
callbackClientSignerPublicKey = "ssh-ed25519 AAAA..."
# grpcTarget = "api.mpcvault.com:443"  # optional, this is the default
```

<Callout type="info">
MPC Vault requires an Ed25519 keypair registered in the MPC Vault console and a running client-signer container (<code>ghcr.io/mpcvault/client-signer:latest</code>). See the <a href="https://docs.mpcvault.com">MPC Vault documentation</a> for setup instructions.
</Callout>

**Turnkey** — Signs transactions via [Turnkey](https://turnkey.com), a key management platform with HD wallet support. Create a wallet in the Turnkey Dashboard and use `signWith` to reference your existing Ethereum address:

```toml lineNumbers
[simplex.signer]
type             = "turnkey"
organizationId   = "your-org-id"
apiPublicKey     = "your-api-public-key"
apiPrivateKey    = "your-api-private-key"
signWith         = "0xYourWalletAddress"
```

<Callout type="info">
Create an API keypair in the Turnkey Dashboard under user details. The <code>signWith</code> field is any Ethereum address from your Turnkey wallet. See the <a href="https://docs.turnkey.com">Turnkey documentation</a> for setup instructions.
</Callout>

### Delegation & Gas Payment

Solver selection requires each solver's EOA to be delegated to the `SolverAccount` contract. Simplex performs this automatically at startup via EIP-7702:

- **Primary path** — builds a no-op UserOperation with an attached EIP-7702 authorization and submits it through the configured bundler. When a paymaster is deployed on the chain — Circle Paymaster (USDC) preferred, then the `SimplexPaymaster` (USDC or USDT) — and the solver holds at least one whole token of a supported stablecoin, the paymaster pays gas in that stablecoin (via EIP-2612 permit, or a small capped approval for tokens without permit support such as BSC stables) so the solver never needs native gas for delegation.
- **Fallback** — if the bundler path fails or the chain has no paymaster, Simplex sends a direct type-0x04 delegation tx using the solver's native balance. On paymaster-less chains it also keeps the ERC-4337 EntryPoint deposit topped up to cover `targetGasUnits` (default 3,000,000) at the current gas price.

No manual steps are required — delegation is idempotent and skipped if the EOA is already delegated to the correct contract.

### Overfill Protection

Detects a computed output that overshoots what the user asked for, which usually means the solver's own pricing is wrong (a bug, a stale cache, a manipulated venue). For every order the solver compares its computed output against `(1 + maxOverfillBps/10000) × user-requested amount` and logs `"Overfill ceiling exceeded — clamp disabled, filling unclamped amount"` when it goes over.

<Callout type="warn">
    **This is detection only — the clamp is disabled.** The solver fills the full computed amount even when it exceeds the ceiling, so there is no per-leg loss bound in the current release. The `maxConsecutiveClamps` halt is wired to the same counter and therefore never fires; `isHalted()` on the library API always returns `false`. Treat the warning as the signal and alert on it.
</Callout>

Defaults are `maxOverfillBps = 500` (≈ 5% ceiling) and `maxConsecutiveClamps = 3`. Override under `[simplex.overfillProtection]`:

```toml lineNumbers
[simplex.overfillProtection]
maxOverfillBps       = 500   # 5% ceiling above user-requested output
maxConsecutiveClamps = 3     # halt threshold; dormant while the clamp is disabled
```

### Vault treasury (ERC-4626)

The optional top-level `[vault]` section configures a **solver-wide stablecoin treasury** backed by ERC-4626 vaults. Any ERC-4626 vault works — for example Aave's `stataToken` for USDC — so idle treasury earns yield while remaining available for fills. Each entry needs a `chain` and a `vault` address; the underlying asset and its decimals are resolved on-chain at startup.

<Callout type="info">
This is distinct from the [`[vault.uniswapV4]`](#uniswap-v4-lp-funding) source, which shares the `[vault]` section. The ERC-4626 treasury sources **stablecoins**; `[vault.uniswapV4]` sources and prices the **exotic** token.
</Callout>

One vault list drives three behaviours:

1. **Sourcing** — when wallet balance is short on a fill, Simplex withdraws the deficit from the solver's vault position. The withdrawal is prepended to the UserOperation as ERC-7821 batch calls, so it is atomic with the fill.
2. **Sweeping** — a timer (`sweepIntervalMs`, default 5 min) waits for wallet balance to reach the `threshold` high-water mark, then deposits everything down to `minBalance`. Size `minBalance` to cover working fill float plus gas/paymaster spend; the `threshold`–`minBalance` gap is the guaranteed minimum sweep size, so balance oscillates between the two without thrashing on dust.
3. **Shutdown** — on stop, positions are kept across restarts by default. Set `redeemOnShutdown = true` on a vault to instead redeem its position back to the underlying asset when the solver stops.

Omit `threshold`/`minBalance` on a vault to make it **withdraw-only** (sourcing + shutdown, no sweeping) for that token.

```toml lineNumbers
[vault]
sweepIntervalMs = 300000   # optional, default 5 min

# Aave stataUSDC on Base — once balance hits $5,000, sweep down to $3,000
[[vault.vaults]]
chain      = "EVM-8453"
vault      = "0xC768c589647798a6EE01A91FdE98EF2ed046DBD6"
threshold  = "5000"
minBalance = "3000"

# Aave stataUSDT on Arbitrum
[[vault.vaults]]
chain      = "EVM-42161"
vault      = "0xa6D12574eFB239FC1D2099732bd8b5dC6306897F"
threshold  = "5000"
minBalance = "3000"
```

| Field | Required | Description |
|---|---|---|
| `chain` | yes | State-machine ID the vault lives on (e.g. `"EVM-8453"`) |
| `vault` | yes | ERC-4626 vault address |
| `threshold` | no | High-water balance (human units) that triggers a sweep down to `minBalance`. Omit to disable sweeping (withdraw-only). |
| `minBalance` | conditional | Wallet floor (human units) the sweep deposits down to. Required when `threshold` is set, and must be less than it. |
| `redeemOnShutdown` | no | Redeem this position back to the underlying asset on shutdown. Defaults to `false` (the position is kept across restarts). |

### Rebalancing

The optional `[rebalancing]` section keeps per-chain, per-asset balances near a configured base. Rebalancing triggers when a balance falls to `(1 - triggerPercentage) × baseBalance`. Base balances are expressed in USD value (treated as $1 per stablecoin), keyed by asset symbol and then by numeric chain ID.

```toml lineNumbers
[rebalancing]
triggerPercentage = 0.5   # trigger when balance ≤ 50% of base

[rebalancing.baseBalances."USDC"]
"1"     = "10000"   # Ethereum: $10k USDC base
"8453"  = "10000"   # Base
"42161" = "10000"   # Arbitrum

[rebalancing.baseBalances."USDT"]
"1"     = "10000"
"8453"  = "10000"
"42161" = "10000"
```

### Allowlist

The optional `[allowlist]` section restricts which order `user` addresses the solver will process. Omit the section entirely to accept orders from all users (the default). When present, only listed users are accepted; address comparisons are case-insensitive.

```toml lineNumbers
[allowlist]
# Users eligible across all source chains
users = [
    "0x1111111111111111111111111111111111111111",
]

# Per-source-chain overrides, keyed by state-machine ID.
# Merged with the global list.
[allowlist.bySource]
# Ethereum-only partner
"EVM-1"     = ["0x2222222222222222222222222222222222222222"]
# Arbitrum-only partner
"EVM-42161" = ["0x3333333333333333333333333333333333333333"]
```

A source chain whose merged set (global `users` + its `bySource` override) is empty rejects every order from that chain.

### Gas Fee Bump

UserOperation gas prices are bumped above the base `gasPrice` by configurable percentages. Defaults are `8%` for the priority fee and `10%` for the max fee. Override under `[simplex.gasFeeBump]`:

```toml lineNumbers
[simplex.gasFeeBump]
# added to base gasPrice for the priority fee
maxPriorityFeePerGasBumpPercent = 8
maxFeePerGasBumpPercent         = 10   # added to base gasPrice for the max fee
```

### Confirmation Policy

Before processing a cross-chain order, Simplex waits for enough block confirmations to guard against chain reorganizations. The number of confirmations scales with order value using a curve — small orders are processed quickly, large orders wait longer. Same-chain orders always proceed without additional confirmation delay.

#### Built-in Defaults

Simplex ships with default confirmation policies for common chains. These apply automatically when no user-configured policy exists for a chain. User-configured policies override the default for that chain. Every configured chain must be covered by a built-in default or a custom entry — a chain with neither fails at startup rather than silently dropping that chain's cross-chain orders at fill time.

| Chain | Chain ID | Min ($1,000) | Max ($100,000) | Block Time |
|---|---|---|---|---|
| Ethereum | 1 | 2 blocks (~24s) | 15 blocks (~3m) | ~12s |
| BNB Chain | 56 | 2 blocks (~6s) | 3 blocks (~9s) | ~3s |
| Polygon | 137 | 2 blocks (~4s) | 32 blocks (~1m) | ~2s |
| Base | 8453 | 2 blocks (~4s) | 90 blocks (~3m) | ~2s |
| Arbitrum | 42161 | 8 blocks (~2s) | 720 blocks (~3m) | ~0.25s |
| Unichain | 130 | 2 blocks (~2s) | 180 blocks (~3m) | ~1s |

Values between the min and max order amounts are linearly interpolated.

#### Custom Overrides

Confirmation policies are configured at the top level under `[confirmationPolicies."<chainId>"]`. Unlisted chains keep their defaults. The curve's `amount` axis is the order's USD value, computed from your pair curves via the USD anchors — honest for non-USD pairs too, so one curve per chain is correctly calibrated for every market on it:

```toml lineNumbers
[confirmationPolicies."1"]     # Ethereum Mainnet (~12s blocks)
points = [
    { amount = "1000",   value = 3  },   # $1k → 3 blocks (~36s)
    { amount = "50000",  value = 15 },   # $50k → 15 blocks (~3m)
    { amount = "100000", value = 20 },   # $100k → 20 blocks (~4m)
]

[confirmationPolicies."56"]    # BSC (~3s blocks)
points = [
    { amount = "1000",   value = 2  },
    { amount = "100000", value = 5  },
]
```

<Callout type="info">
Confirmation policies are optional — built-in defaults cover Ethereum, BNB Chain, Base, Arbitrum, Polygon, and Unichain. Custom <code>[confirmationPolicies."&lt;chainId&gt;"]</code> entries override the default for that chain only.
</Callout>

### RPC Quorum

Each `[[chains]]` entry declares its RPC endpoints as a non-empty array in `rpcUrls`. Simplex validates the array at startup and rejects it if any two URLs share a hostname, so a "quorum" of aliases pointing at the same upstream is caught before the solver starts.

```toml lineNumbers
[[chains]]  # Ethereum
rpcUrls = [
    "https://eth-mainnet.g.alchemy.com/v2/YOUR_KEY",
    "https://mainnet.infura.io/v3/YOUR_KEY",
    "https://rpc.ankr.com/eth/YOUR_KEY",
]
bundlerUrl = "https://..."
```

When you configure more than one URL, every quorum-checked read (`eth_getLogs`, `eth_blockNumber`, receipt during confirmation counting) is accepted only when a **BFT quorum** of your endpoints — `floor(2N/3) + 1` of them — agree on the result. If the quorum can't be formed — endpoints down, throttled, or disagreeing — the call fails loudly with a `QuorumError` and the scan cursor does not advance. There is no pausing or ejection state: each call independently queries every endpoint and resolves the moment the quorum is met, so a chronically slow or hung endpoint settles out of band and never stalls the confirmation hot path, let alone shrinks the quorum. A provider that *answers with divergent data* is never special-cased away; it simply fails to join the agreeing group, which is what keeps a lying or reorged endpoint detectable rather than authoritative.

Log agreement compares only the consensus-relevant JSON-RPC fields (`address`, `blockHash`, `blockNumber`, `data`, `logIndex`, `removed`, `topics`, `transactionHash`, `transactionIndex`), sorted by `(blockNumber, logIndex, transactionHash)`; provider-added extras like `blockTimestamp` are dropped so debug metadata can't manufacture a disagreement. `getBlockNumber` returns the highest block that a full quorum has indexed, so the scanner never runs ahead of quorum-supported state.

The quorum is exactly the endpoints you configure — Simplex never adds third-party endpoints of its own. **To tolerate a faulty provider you need at least four endpoints** — with three, the threshold is still three and any single failure halts scanning. Quorum reads are the only multi-endpoint path; latency-sensitive and write paths (gas estimation, balance reads, transaction submission) use your first healthy endpoint.

#### Quorum-checked confirmations

Cross-chain orders wait for source-chain confirmations (per the confirmation policy) before a bid is submitted. That count is computed with the same quorum: every endpoint is asked for the transaction receipt and its chain head, and the transaction is confirmed only when a quorum agrees on the *inclusion block* — the receipt's `(blockHash, blockNumber)`. The depth is the quorum head of that agreeing group. Crucially, an endpoint answering **"receipt not found"** is a valid *no* vote — it's responsive but doesn't see the transaction — not a failure: so if the transaction is reorged out, the honest endpoints report not-found, no group reaches quorum, and the count does not advance. A minority still serving a stale or fabricated receipt can never reach the quorum.

#### Why this matters for cross-chain orders

On a cross-chain fill, Simplex observes an `OrderPlaced` (or `PartialFill` / `OrderFilled`) event on the source chain and then commits capital on the destination chain. Unlike same-chain fills — where the destination `fillOrder` call will revert if the source-chain order does not exist — cross-chain bids submitted through Hyperbridge are evaluated from the solver's own reading of source-chain state. A single RPC is therefore both an availability and an integrity choke point: if it lies about which orders were placed, the solver can be induced to pay out against events that never happened, and there is no on-chain safety net to catch it after the fact.

<Callout type="warn">
Co-opted RPC nodes are not hypothetical. LayerZero has publicly disclosed an incident where an RPC endpoint serving part of their relaying path was compromised — see [LayerZero's post-mortem thread](https://x.com/LayerZero_Core/status/2046081551574983137?s=20). Quorum queries turn that failure mode from "one bad node silently succeeds" into "one bad node fails the batch and halts the scan".
</Callout>

The practical guidance is to configure **at least two organisationally independent providers** (e.g. Alchemy **and** Infura, not two Alchemy regions) for every chain that can act as a source of a cross-chain order. Each additional independent provider raises the bar for an attacker from "compromise one vendor" to "compromise all of them simultaneously for the duration of the fill window". The cost is a slightly higher RPC bill and the tail latency of the slowest provider in each batch; the benefit is that event-driven bids are only acted on when every independent provider agrees on what the source chain actually emitted.

## Requirements

You need an EVM wallet (configured via `[simplex.signer]`) funded with native tokens for gas and stablecoins to fill orders with — minimum $10,000 equivalent per chain is a reasonable starting point. For cross-asset pairs, also hold the non-USD token on each chain, plus a Substrate account with BRIDGE tokens for Hyperbridge extrinsic fees. A successful bid also locks a deposit, reclaimed by retracting the bid. Simplex retracts automatically when it sees the order filled, and a periodic sweep retries anything that failed — but **stopping the solver does not sweep**, so a bid still unretracted at shutdown stays locked until the next run picks it up. That is why the bid store must be durable.

RPC endpoints must be from a premium provider (Alchemy Pro, Infura Growth+, QuickNode Pro). Archive node access is required for storage slot queries and gas simulation. Free-tier RPCs will not work reliably. For chains that can source cross-chain orders, configure at least two organisationally independent providers in `rpcUrls` — see [RPC Quorum](#rpc-quorum).

## Troubleshooting

For verbose output, set `logging = "debug"` in `[simplex]`. Report bugs to the Hyperbridge GitHub with full logs (redact private keys).

### **No profitable strategy found**
Gas prices may be too high relative to the order fee, or your pair curves may be set too conservatively. Check balances on the destination chain and review current gas prices.

---

### **Insufficient token balances**
Deposit more stablecoins (and non-USD tokens for cross-asset pairs) on the destination chains.

---

### **RPC rate limiting (429 errors)**
Switch to a premium RPC provider or reduce `maxConcurrentOrders`.

---

### **Bid submission fails**
Confirm `substratePrivateKey`, `hyperbridgeWsUrl`, and `bundlerUrl` are set in `[simplex]`, and that your Substrate account has BRIDGE tokens. On chains with a paymaster (Circle or Simplex), make sure the solver's smart account holds at least 1 USDC (or 1 USDT, for the `SimplexPaymaster`) so the paymaster can cover gas. On chains without any paymaster, the solver needs native balance — Simplex automatically tops up the ERC-4337 EntryPoint deposit to cover `targetGasUnits` (default 3M) at current gas price. If using MPC Vault, verify the client-signer container is running and reachable.

---

### **Funding venue withdrawal failed**
Confirm the LP position has sufficient liquidity and that the token addresses match the pair's configured tokens. Verify the `tokenId` exists and is owned by the solver account. Check logs for specific revert reasons.

---

### **Venue price returns null / bid-ask not updating**
Confirm the configured positions contain a pool that pairs the exotic token with **USDC or USDT**. Pools with other quote tokens cannot derive a USD price from the Uniswap V4 venue. Check that the position's `tokenId` is valid and owned by the solver.

---

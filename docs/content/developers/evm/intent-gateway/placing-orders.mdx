# Placing Orders

This guide places a USDC → cNGN order from start to finish. It uses the SDK's `executeBest()` flow: you approve the input token, sign one `placeOrder` transaction, and the SDK runs the solver auction and submits the selected solver's fill.

Use the same flow for other supported token pairs. The only difference between the two modes is the destination chain:

| Mode | `sourceChain` | `destChain` | Settlement |
| --- | --- | --- | --- |
| Same-chain | Base, for example | The same Base chain instance | Atomic on one chain; partial fills are possible |
| Cross-chain | Ethereum, for example | Arbitrum, for example | The solver fills on the destination, then Hyperbridge releases the source-chain escrow; fills are all-or-nothing |

## Before you begin

You need:

- An RPC URL for the source chain, and one for the destination chain if this is cross-chain.
- An ERC-4337 bundler URL for the destination chain. This is required in both modes because solvers submit fills as UserOperations.
- A source-chain wallet with the USDC input amount and enough native token for transaction gas and the quoted solver fee.
- A Hyperbridge-supported source and destination chain. `EvmChain.create()` rejects an RPC for a chain without a known Hyperbridge deployment.

Install the SDK and viem:

```bash
npm install @hyperbridge/sdk viem
```

<Callout type="info">
This example uses the SDK's built-in Phantom quote for USDC/cNGN. It is the recommended way to get the input and output amounts for that pair. For another pair, obtain a quote from your pricing source and put its amounts in the same order shape.
</Callout>

## How `placeOrder` works

Everything the SDK does in this guide ends in one contract call on the source chain:

```solidity
function placeOrder(Order calldata order, bytes32 graffiti) external payable;
```

### Data structures

```solidity
struct Order {
    bytes32 user;           // Set by placeOrder to msg.sender
    bytes source;           // Set by placeOrder to current chain ID
    bytes destination;      // Target chain state machine ID
    uint256 deadline;       // Block number deadline for fills
    uint256 nonce;          // Set by placeOrder (auto-incrementing)
    uint256 fees;           // Solver fee in the fee token
    address session;        // Session key for solver selection (address(0) to disable)
    DispatchInfo predispatch; // Pre-order execution (swap before escrow)
    TokenInfo[] inputs;     // Tokens escrowed from user
    PaymentInfo output;     // What the solver must provide
}

struct TokenInfo {
    bytes32 token;   // Token address as bytes32; bytes32(0) = native token
    uint256 amount;
}

struct PaymentInfo {
    bytes32 beneficiary;  // Recipient of output tokens
    TokenInfo[] assets;   // Output tokens solver must provide
    bytes call;           // Optional calldata executed after fill (via CallDispatcher)
}

struct DispatchInfo {
    TokenInfo[] assets;   // Assets sent to CallDispatcher before order
    bytes call;           // Calldata for pre-order execution
}
```

<Callout type="info">
In the SDK, `TokenInfo.token` and `output.beneficiary` are standard 20-byte EVM addresses (`0x…`). The SDK left-pads them to `bytes32` when encoding the contract call — you do not need to pad them yourself.
</Callout>

### Deadline

`order.deadline` is a **block number on the destination chain**. Calculate it from the destination chain's current block number, because fills and expiry are checked there. This applies to every order; for a same-chain order the source and destination are simply the same chain.

```typescript lineNumbers title="deadline.ts" icon="typescript"
// Choose a window appropriate for the destination chain's block time.
const deadline = (await destChain.client.getBlockNumber()) + 200n
```

<Callout type="warn">
For cross-chain orders, do not calculate `deadline` from `sourceChain`. Source and destination block heights are independent, and the destination gateway compares `order.deadline` with its own `block.number` when a solver fills the order.
</Callout>

### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>

### Graffiti

Every `placeOrder` call accepts a `graffiti` argument — a `bytes32` tag that identifies the frontend or integration that originated the order. It is passed as calldata and enables on-chain attribution of orderflow to specific integrators for revenue sharing.

Encode your integrator identifier once and pass it as the second argument to `executeBest()` — the rest of this guide uses it:

```typescript lineNumbers title="graffiti.ts" icon="typescript"
import { stringToHex, padHex } from "viem"

// Encode your integrator identifier as a right-padded bytes32
const MY_GRAFFITI = padHex(stringToHex("my-app"), { size: 32, dir: "right" })
```

An order placed without a graffiti (the SDK defaults to a zero `bytes32`) is unattributed — it cannot be credited to your integration for revenue share.

### Quote the swap and create the order

`quoteIntent()` reads Phantom price snapshots through the indexer attached in setup. For an exact-input order, `amountIn` is the amount you send and `amountOut` is the quoted output you require from the solver.

```typescript title="create-order.ts" lineNumbers
import { type Order } from "@hyperbridge/sdk"
import { parseUnits, zeroAddress, zeroHash } from "viem"

const sourceId = sourceChain.config.stateMachineId
const destId = destChain.config.stateMachineId

// These resolve the configured USDC and cNGN deployments for each chain.
// Do not reuse a source-chain token address on the destination chain.
const usdcSource = sourceChain.configService.getUsdcAsset(sourceId)
const cngnDestination = destChain.configService.getCNgnAsset(destId)
if (!cngnDestination) throw new Error(`cNGN is not configured on ${destId}`)

const quote = await gateway.quoteIntent({
  tokenIn: usdcSource,
  tokenOut: cngnDestination,
  amountIn: parseUnits("100", 6), // 100 USDC
})

const order: Order = {
  // The gateway stamps user, source, and nonce; the SDK creates a one-time session key.
  user: zeroHash,
  source: sourceId,
  destination: destId,
  // This is always a DESTINATION-chain block number.
  deadline: (await destChain.client.getBlockNumber()) + 200n,
  nonce: 0n,
  // We'll set this in the fees step below.
  fees: 0n,
  session: zeroAddress,
  predispatch: { assets: [], call: "0x" },
  inputs: [{ token: usdcSource, amount: quote.amountIn }],
  output: {
    beneficiary: account.address,
    assets: [{ token: cngnDestination, amount: quote.amountOut }],
    call: "0x",
  },
}
```

The quote already accounts for the gateway protocol fee. The contract deducts that fee from `order.inputs` when it escrows the USDC, so use `quote.amountIn` and `quote.amountOut` exactly as returned. Do not deduct the protocol fee again.

</Step>
<Step>

### Approve the input token

The source-chain gateway needs permission to transfer the ERC-20 input. Approve the gross input amount before starting the order. You can skip this step only if the wallet has already granted a sufficient allowance.

```typescript title="approve-usdc.ts" lineNumbers
import { erc20Abi } from "viem"

const sourceGateway = sourceChain.configService.getIntentGatewayAddress(sourceId)
const approvalHash = await walletClient.writeContract({
  address: usdcSource,
  abi: erc20Abi,
  functionName: "approve",
  args: [sourceGateway, quote.amountIn],
})

await sourceChain.client.waitForTransactionReceipt({ hash: approvalHash })
```

If your input is the native token rather than an ERC-20, do not approve it. The `AWAITING_PLACE_ORDER` update reports native input amounts as `value` — the placement transaction carries that plus any native fee payment.

</Step>
<Step>

### Decide how `order.fees` is paid

`order.fees` is the gas cost the solver spends on filling the order, denominated in the source chain's Hyperbridge fee token. For a cross-chain order it also covers the relayer that delivers the `RedeemEscrow` settlement message back to the source chain. It is not the protocol fee and it is not your wallet's transaction gas.

Quote it with `quoteOrderFees()` and set it on the order:

```typescript title="quote-order-fees.ts" lineNumbers
const { fees, nativeValue, feeToken } = await gateway.quoteOrderFees(order)
order.fees = fees
```

Then pick how it gets paid and confirm the wallet can cover it.

#### Native token

The placement transaction carries `nativeValue` extra wei, which the gateway swaps into the fee token through its configured router (unused native is refunded). Check the balance now; the placement step adds `nativeValue` to the transaction:

```typescript title="check-native-fee.ts" lineNumbers
const nativeBalance = await sourceChain.client.getBalance({ address: account.address })
if (nativeBalance < nativeValue) throw new Error("Insufficient native balance for the solver fee")
```

The wallet still pays normal transaction gas on top of this value.

#### Fee token

Approve the gateway for exactly `fees` of `feeToken` — it pulls the fee via the allowance at placement, and nothing extra rides on the transaction's value:

```typescript title="check-fee-token.ts" lineNumbers
import { erc20Abi } from "viem"

const [feeBalance, feeAllowance] = await Promise.all([
  sourceChain.client.readContract({
    address: feeToken,
    abi: erc20Abi,
    functionName: "balanceOf",
    args: [account.address],
  }),
  sourceChain.client.readContract({
    address: feeToken,
    abi: erc20Abi,
    functionName: "allowance",
    args: [account.address, sourceGateway],
  }),
])
if (feeBalance < fees) throw new Error("Insufficient fee token balance")

if (feeAllowance < fees) {
  const hash = await walletClient.writeContract({
    address: feeToken,
    abi: erc20Abi,
    functionName: "approve",
    args: [sourceGateway, fees],
  })
  await sourceChain.client.waitForTransactionReceipt({ hash })
}
```

If the order is cancelled before a full fill, `order.fees` is refunded with the remaining escrow; if it fills, it is released to the solver.

<Callout type="info">
You may set `order.fees` higher than this policy to make the order more attractive to solvers. A smaller fee can leave the order with no viable bids; the SDK cannot guarantee a fill at any fee level.
</Callout>

</Step>
<Step>

### Place the order and let the SDK execute it

`executeBest()` is a bidirectional async generator. Its first update contains the exact `placeOrder` calldata and the order's native-token input amounts as `value` (`0n` for this USDC order). Add the `nativeValue` from your fee quote when paying the solver fee in native token, then sign and return the signed transaction to the generator.

```typescript title="place-and-execute.ts" lineNumbers
import { IntentOrderStatus } from "@hyperbridge/sdk"

const run = gateway.executeBest(order, MY_GRAFFITI, {
  auctionTimeMs: 15_000,
  pollIntervalMs: 5_000,
})

const first = await run.next()
if (first.done || first.value.status !== IntentOrderStatus.AWAITING_PLACE_ORDER) {
  throw new Error("Expected placement transaction")
}
const { to, data, value } = first.value

// Paying the fee in native token: add nativeValue from quoteOrderFees.
// Paying with the fee-token approval: txValue is just value.
const txValue = value + nativeValue

const signedPlacementTx = await walletClient.signTransaction({
  to,
  data,
  value: txValue,
  type: "eip1559",
})

// This waits for OrderPlaced and returns the canonical, finalized order.
const placed = await run.next(signedPlacementTx)
if (placed.done || placed.value.status !== IntentOrderStatus.ORDER_PLACED) {
  throw new Error("Order was not placed")
}

const finalizedOrder = placed.value.order
console.log("Placement transaction:", placed.value.receipt.transactionHash)
console.log("Order commitment:", finalizedOrder.id)
// Persist finalizedOrder: it is required to resume or cancel later.

for await (const update of run) {
  switch (update.status) {
    case IntentOrderStatus.AWAITING_BIDS:
      console.log("Waiting for solver bids")
      break
    case IntentOrderStatus.BID_SELECTED:
      console.log("Solver fill submitted:", update.transactionHash)
      break
    case IntentOrderStatus.PARTIAL_FILL:
      // Same-chain only. The SDK automatically seeks a fill for the remainder.
      console.log("Partial fill; remaining:", update.remainingAssets)
      break
    case IntentOrderStatus.FILLED:
      console.log("Swap complete:", update.transactionHash)
      break
    case IntentOrderStatus.EXPIRED:
      console.warn("Order was not fully filled; cancel it to reclaim its remaining escrow.")
      break
    case IntentOrderStatus.FAILED:
      // Informational: the SDK continues polling and retrying until filled or expired.
      console.warn("Retryable fill failure:", update.error)
      break
  }
}
```

</Step>

## Smart accounts: batch the approvals and placement

Smart accounts can turn the normal two-transaction ERC-20 path (approve input, then place) into one atomic UserOperation. This has three useful properties:

- **No standing unlimited allowance.** Approve exactly `quote.amountIn` for the input and, when paying the fee token directly, exactly `order.fees` for the fee token.
- **No approval front-running window.** If the account batches the approvals and `placeOrder`, the gateway can use each allowance only in that same atomic operation.
- **One user confirmation.** The user signs one smart-account operation rather than separately approving and placing.

Start the generator first so the SDK has created the final placement calldata. Then add the approval call(s) immediately before that placement call in your smart account's batch API:

```typescript title="smart-account-batch.ts" lineNumbers
import { encodeFunctionData, erc20Abi } from "viem"

const run = gateway.executeBest(order, MY_GRAFFITI, {
  auctionTimeMs: 15_000,
  pollIntervalMs: 5_000,
})
const first = await run.next()
if (first.done || first.value.status !== IntentOrderStatus.AWAITING_PLACE_ORDER) {
  throw new Error("Expected placement transaction")
}

const exactInputApproval = {
  to: usdcSource,
  value: 0n,
  data: encodeFunctionData({
    abi: erc20Abi,
    functionName: "approve",
    args: [sourceGateway, quote.amountIn],
  }),
}

const placementCall = {
  to: first.value.to,
  // Native inputs; the batched fee-token approval covers order.fees.
  value: first.value.value,
  data: first.value.data,
}

// Adapt this one line to your smart-account provider:
// - EIP-5792 wallets: wallet_sendCalls / walletClient.sendCalls
// - ERC-4337 SDKs: sendUserOperation({ calls: [...] })
const { transactionHash } = await smartAccount.executeBatch([
  exactInputApproval,
  placementCall,
])

// Give the SDK the EVM transaction hash that contains placeOrder, not only a UserOp hash.
const placed = await run.next(transactionHash)
```

`smartAccount.executeBatch` is intentionally adapter-shaped pseudocode: smart-account providers name the method differently, but the two calls and their order are the same. An EIP-5792 `wallet_sendCalls` integration should wait for the batch status and pass the transaction hash from the receipt containing `placeOrder` to `run.next()`.

If you pay `order.fees` in the fee token, insert a second exact fee-token approval immediately before `placementCall`:

```typescript title="smart-account-fee-token-approval.ts" lineNumbers
const exactFeeApproval = {
  to: feeToken,
  value: 0n,
  data: encodeFunctionData({
    abi: erc20Abi,
    functionName: "approve",
    args: [sourceGateway, order.fees],
  }),
}

await smartAccount.executeBatch([
  exactInputApproval,
  exactFeeApproval,
  placementCall,
])
```

Some ERC-20s require an allowance to be reset to zero before changing a non-zero allowance. For those tokens, add `approve(sourceGateway, 0n)` before the exact approval in the same batch. Do not use this reset on tokens that do not require it unless your token integration specifies it.

## What you pay

The placement transaction has four distinct costs.

| Cost | Paid by | How it is handled |
| --- | --- | --- |
| Input amount | You, on the source chain | `quote.amountIn` USDC is transferred into escrow after approval. |
| Protocol fee | You, from the input amount | 5 bps is deducted at successful placement. It is not returned on expiry or cancellation. The quote already accounts for it. |
| Solver fee (`order.fees`) | You, in the Hyperbridge fee token | The gas cost the solver spends on filling the order — paid in the fee token directly, or in native token that the gateway swaps for the fee token. For cross-chain orders it includes the `RedeemEscrow` relayer fee. |
| Source-chain transaction gas | You, in native token | Paid by the wallet when it submits the approval and placement transactions. |

Do not manually add the protocol fee to `order.fees`: they are different charges. `order.fees` pays the solver and, cross-chain, the settlement relayer; the protocol fee is deducted from the input before the order commitment is created.

<Callout type="warn">
The placement transaction's `msg.value` is the `value` from `AWAITING_PLACE_ORDER` — the order's native-token input amounts — plus the quoted `nativeValue` when paying the solver fee in native token. Never zero out `value`.
</Callout>

## Completion and recovery

For a same-chain swap, `FILLED` means the output was delivered and the input escrow released to the solver. Partial fills can occur before the final update.

For a cross-chain swap, `BID_SELECTED` means the solver fill was submitted on the destination. Hyperbridge then delivers the settlement message and releases the source escrow asynchronously; cross-chain fills cannot be partial. Persist `finalizedOrder`, and if the deadline expires before the order completes, reclaim unfilled escrow with the [cancellation guide](./cancelling-orders).

For advanced order fields, custom bid selection, native-token inputs, and pre/post-dispatch calls, refer to the SDK API reference or contact the Hyperbridge team.
